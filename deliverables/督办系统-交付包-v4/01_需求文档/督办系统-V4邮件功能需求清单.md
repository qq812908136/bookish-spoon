# 督办系统 V4 迭代 —— 发送邮件功能需求清单

> **文档状态**：待确认（SPEC 锁定前不写业务代码）
> **版本**：v1.0
> **日期**：2026-09-03
> **来源**：A–I 共 9 组主题访谈（55 个决策点）收口结果
> **适用范围**：V4 迭代「发送邮件」功能

---

## 0. 一句话定义

> 在现有站内信之外，增加一条**邮件通知通道**：任务逾期时自动给负责人发提醒邮件、给管理员发每日汇总日报；管理员与任务创建人可在任务详情页手动发送提醒邮件。所有邮件**先落库进队列，再由定时任务扫描发送**，全程可查、可重发、可熔断。

**核心痛点**（A1）：站内信容易被忽略，邮件能真正落到收件箱。
**成功标准**（A2）：可用即可 —— 能发出去 + 有发送记录。

## 1. 功能目标与边界

### 1.1 目标

| 编号 | 目标 |
|---|---|
| G-1 | 预警通知**触达到人**——走出系统，落到收件箱 |
| G-2 | 发送结果**可查**——管理员能看见成功/失败，失败可重发 |
| G-3 | 故障**可见**——配置错误或触发风控时自动熔断并告警，不静默失败 |
| G-4 | 配置**零侵入**——不配 SMTP 时系统行为完全不变（沿用既有铁律） |

### 1.2 明确不做（本轮边界）

| 编号 | 不做的事 | 原因 |
|---|---|---|
| N-1 | **不做邮件内审批**（不能在邮件里点链接直接闭环/改状态） | 需引入免登录签名 Token，与 DEF-002（全站无 CSRF）整改方向冲突 |
| N-2 | **不接收/解析入站邮件**（只发不收） | 入站需常驻轮询 + MIME 解析，是独立子系统 |
| N-3 | **不支持附件** | 涉及文件路径、大小限制、病毒风险，收益低于成本（表结构预留字段） |
| N-4 | **不用 HTML 富文本**，只发纯文本（text/plain） | HTML 邮件更易判垃圾邮件，各客户端渲染差异大 |
| N-5 | **不做外部收件人** | 防被当垃圾邮件发射器；A1 目标是"提醒到人"，不涉及对外协同 |
| N-6 | **不做批量群发** | A4 定为"自动 + 手动"档，不含群发 |
| N-7 | **不做模板在线编辑** | 同上，模板固定，仅落款可配 |
| N-8 | **不做到达率统计 / 打开追踪 / 回执解析** | A2 成功标准为"可用即可"，非量化到达 |

### 1.3 功能粒度

**档位：自动预警邮件 + 手动发送**（A4-②）

- 自动：仅"已逾期"层（默认），用户可自愿升级订阅等级（C1-③④）
- 手动：任务详情页「发送提醒邮件」按钮（C3-①）

## 2. 触发场景

### 2.1 自动触发

| # | 场景 | 触发点（代码挂钩位置） | 收件人 | 去重键 |
|---|---|---|---|---|
| T-1 | **任务逾期** | `warning_engine.trigger_overdue_warning()` | 负责人（合并成一封） | 任务+收件人+类型+日期 |
| T-2 | **任务分配 / 改派** | 任务创建/改派逻辑 | 新负责人 | 任务+收件人+类型+日期 |
| T-3 | **管理员日报** | 每日 09:00 扫描后 | 所有在职管理员 | 收件人+日期 |

**不触发的场景**：任务闭环、任务撤销、即将到期（除非用户订阅等级升级）、长期待激活（除非用户订阅等级升级）、任务分配/改派/状态变更产生的普通站内信。

### 2.2 挂钩策略（C2-②）

- ⚠️ **不修改** `models.create_message()`。改它会导致"任务分配通知""状态变更通知""管理员批示"等全部变成邮件，把高价值低频消息淹没。
- ✅ 只在 `warning_engine.py` 的两个出口（`_send_merged_warnings()` / `trigger_overdue_warning()`）挂钩，**额外往 `email_queue` 表插一条记录**。
- ✅ 任务分配/改派场景在对应 route 中单独插入队列。
- 邮件 = 预警引擎的一个**输出通道**，职责清晰；预警规则改动只需改一处。

### 2.3 手动触发（C3-①）

- **入口**：任务详情页新增「发送提醒邮件」按钮
- **权限**：管理员 + 该任务的创建人（H1-②）
- **内容**：固定模板 + 可选留言（≤200 字纯文本）
- **冷却**：同一任务 + 同一操作人，**5 分钟内只能发一次**，按钮置灰并显示倒计时（F4-②）
- **语义**：单任务单封，不参与 F2 的合并逻辑

### 2.4 发送时机（B6-③ + C4-②）

**先落库为"待发送"，由定时任务扫描发送。**

- 扫描周期：**每 5 分钟**，**复用现有 `scheduler.py` 的逾期扫描循环，零新增线程**（C4-②）
- 每轮最多发送 **20 封**（F3-②），余下顺延到下一个 5 分钟窗口
- 页面永不卡顿；失败记录天然留在队列里可重试；天然支持限频

**预估邮件量**：20 位负责人 × 1 封合并件 + 10 位管理员 × 1 封日报 ≈ **30 封/天**（对比不合并方案 500 封/天，规避个人邮箱风控）。

## 3. 收件人规则与模板

### 3.1 收件人规则

| 规则编号 | 内容 |
|---|---|
| R-1 | 预警邮件收件人 = **负责人 + 所有在职管理员**（D1-①），受各自订阅开关约束 |
| R-2 | **管理员只收每日汇总日报一封**，不收单任务零散邮件（D2-②） |
| R-3 | **每人单独发一封，不用 CC**（D3-①）——配合落库队列，可精确追踪与重发单封 |
| R-4 | **只发给系统内已注册用户**，不支持外部邮箱（D5-①） |
| R-5 | 收件人**无邮箱或账号已停用** → 跳过，并在邮件状态页显示"N 位用户未填邮箱"，可展开看名单（D4-②） |
| R-6 | **同一负责人多个逾期任务合并成一封**清单邮件（F2-②）；手动发送不合并 |

### 3.2 用户订阅等级（D6-②）

`users.mail_notify_level`，**默认"仅逾期"**：

| 值 | 含义 | 覆盖场景 |
|---|---|---|
| `off` | 关闭 | 不收任何邮件（仍收站内信） |
| `overdue` | **仅逾期**（默认） | T-1 逾期 |
| `overdue_due` | 逾期 + 即将到期 | T-1 + 即将到期预警 |
| `all` | 全部预警 | T-1 + 即将到期 + 长期待激活 |

> 管理员的日报（T-3）同样受此开关约束 —— 设为 `off` 的管理员不收日报。

### 3.3 发送频率与去重（F 组）

| 规则 | 值 |
|---|---|
| **F1 提醒节奏** | 逾期第 1/2/3 天每天一封，之后每 3 天一封（第 6/9/12… 天） |
| **F2 合并** | 同一负责人多个逾期任务 → 合并成一封 |
| **F3 限速** | 每轮扫描最多 20 封 |
| **F4 手动冷却** | 同一任务+同一操作人 5 分钟 |
| **F5 总次数上限** | **无上限**，一直提醒到任务闭环 / 撤销 |
| **C6 去重键** | **邮件独立去重**（任务+收件人+类型+日期），**不与站内信共用** |

> ⚠️ **C6 为什么必须独立**：B5 定了"未配置邮件时静默降级"。若共用去重键，在未配邮件的那些天里站内信照发、去重名额被消耗，等某天配好 SMTP，当天就再也发不出邮件了（系统认为"今天发过了"）。

### 3.4 邮件模板（E 组）

#### 3.4.1 逾期提醒邮件（发给负责人，可能合并多条）

**主题**（E1-①）：
```
[督办系统] 任务逾期提醒：{任务标题}
```
> 单任务时用任务标题；合并邮件时标题为 `[督办系统] 任务逾期提醒：您有 {N} 项任务已逾期`。
> 任务标题超 20 字自动截断加省略号（手机端主题行超约 30 汉字会被截断）。

**正文**（E2-① 精简版）：
```
您好，{负责人姓名}：

您有 {N} 项任务已逾期，请尽快处理：

1. {任务标题}
   负责人：{负责人}
   截止日期：{截止日期}（已逾期 {天数} 天）
   优先级：{优先级}
   创建人：{创建人}

2. ...

请登录督办系统查看详情。

—— 本邮件由督办系统自动发送，请勿直接回复。
```

**不含**：任务描述全文、最新进度、任务详情链接（E3-② 不放链接）。

**主题**：`[督办系统] 督办提醒：{任务标题}`

**正文**：固定模板（同 3.4.1 单任务版）+ 操作人留言段落：
```

```

#### 3.4.5 模板可配置性（E4-①）

- **模板骨架固定写死在代码中**，改措辞需改代码
- **仅落款可配**：`MAIL_FOOTER`，默认值 `本邮件由督办系统自动发送，请勿直接回复。`（E5-①）
- 编码：UTF-8；`Content-Type: text/plain; charset=utf-8`

## 4. 异常与重试策略

### 4.1 状态机

```
待发送(pending) → 发送中(sending) → 成功(sent)
                       ↓
                    失败(retrying) → 待发送（重试，次数+1）
                       ↓ 重试次数 > 3
                    永久失败(failed)
```

### 4.2 重试规则（G1-①）

- 最多重试 **3 次**
- 间隔递增：**5 分钟 → 15 分钟 → 30 分钟**
- 超过 3 次 → 标记 `failed`（永久失败）

### 4.3 错误分类处理（G2，确认）

| 错误类型 | 典型码 | 处理 | 理由 |
|---|---|---|---|
| 网络超时 / 连接被拒 | — | **重试** | 临时故障 |
| 超出发信限额 | 452 / 454 | **延迟较久后重试** | 等限流窗口过去 |
| **认证失败** | **535** | **立即判死 + 熔断告警** | 密码错误，重试无意义且会触发风控 |
| 收件人被拒 | 550 | **立即判死** | 地址不存在 |
| 被判定为垃圾邮件 | — | **立即判死 + 告警** | 内容有问题，重试加重处罚 |

### 4.4 熔断机制（G3-③ + G4-②）

**熔断一：认证失败立即熔断（G3-③）**

> ⚠️ 这是本轮**最关键的防护**。若密码错误而系统不知情，每 5 分钟取 20 封去试，一天即 5760 次失败登录 —— 极可能被服务商判定异常登录并**封停该邮箱账号**。

触发条件：检测到 535 认证失败等**永久性错误**
动作：
1. 写日志
2. 设置页顶部**红色横幅**：「邮件发送已自动暂停：SMTP 认证失败，请检查配置」
3. **自动暂停整个邮件功能**，队列停止扫描
4. 管理员修好配置后**手动点「恢复」**

**熔断二：连续失败通用熔断（G4-②）**

- 触发条件：**连续失败 10 次**
- 动作：暂停 **60 分钟**，之后自动恢复试探；再次失败则再次暂停
- 覆盖场景：服务商整体故障、断网等错误码不明确的情况

### 4.5 重启与停机处理

| 场景 | 处理 | 依据 |
|---|---|---|
| **G5 重启时队列卡在"发送中"** | 全部**重置为"待发送"**重发 | **"宁可重复、不可丢失"**（已确认）。极端情况下收件人可能收到两封相同提醒，概率极低、代价可接受 |
| **G6 停机期间漏掉的邮件** | 队列里已生成的**继续发**；**不追溯补生成**停机期间的预警 | 已存在的是"答应了要发的"；补生成会造成周一涌进三天提醒的糟糕体验，且任务仍逾期，下周期自然再提醒 |

### 4.6 失败可见性（G7-①）

邮件状态页提供**「失败清单」**：列出收件人 / 失败原因 / 时间，支持**一键重发**。

> 底线原则：**邮件功能最糟糕的失败模式不是报错，而是静默失败**。系统以为发了、管理员以为通知到位了，实际对方根本没收到。

## 5. 权限与安全要求

| 编号 | 要求 | 依据 |
|---|---|---|
| **P-1** | 手动发信权限 = **管理员 + 该任务的创建人**（负责人不能给自己发） | H1-② |
| **P-2** | 发送记录：管理员看全部；普通用户在个人设置里**只看"发给我的"** | H2-① |
| **P-3** | **邮箱地址仅本人 + 管理员可见**。用户列表页**不显示邮箱列**；用户编辑页与个人设置页显示 | H3-① |

| **P-6** | 手动发送留审计：发信记录加**操作人字段**（自动发送时为空，手动时记 user_id） | H6-① |
| **P-7** | **SMTP 密码在任何情况下不写入日志**（含报错时）—— 硬约束 | I3 |
| **P-8** | 日志**只记元数据**（时间/收件人/类型/成功失败/错误码），**不记邮件正文** | I3-① |
| **P-9** | 纯文本邮件，不存在 XSS 风险 | N-4 附带收益 |

## 6. 服务商、凭据与存储

### 6.1 服务商选型（B1）

- 用户选择：**个人邮箱 SMTP**（QQ / 163，用**授权码**而非登录密码）
- **实现方式：通用 SMTP 配置**（六字段抽象）—— 只有 `host / port / username / password / use_ssl / use_tls`，个人邮箱只是"填进去的一组值"。将来换企业邮箱**只改配置，零改代码、零重打包**。

### 6.2 已告知的风险（用户已知悉并接受）

1. **发信限额与风控** —— 个人邮箱有日发送上限；已通过 F2 合并 + D2 日报压缩到约 30 封/天规避
2. **绑定在个人身上** —— SMTP 授权码属于某个具体同事的邮箱，其离职/改密码会导致全系统邮件中断
3. **发件人形象** —— 收件人看到个人地址，可信度较低，进垃圾箱概率更高

### 6.3 发件人策略（B2-③）

- **共用发件箱**统一发信（`MAIL_FROM_ADDR` / `MAIL_FROM_NAME`）
- **`Reply-To` 指向具体操作人** —— 收件人点"回复"回到真人

### 6.4 凭据存储（B3 + B4-乙）

**三级优先级**：系统环境变量 > `.env` 文件 > 设置页填的值（加密存库）

- **默认路径**：`.env` 文件（位于 `BASE_DIR`，与 `SECRET_KEY` 同机制）
- **可选覆盖**：管理员在设置页填写 → 加密存库
- **加密算法（乙方案）**：`hashlib.pbkdf2_hmac` 从现有 `data/secret.key` 派生 32 字节密钥，再用 `shake_256` 生成密钥流做 XOR 对称加密。**全部 Python 内置库，零新依赖、不用重打包依赖。**

⚠️ **乙方案的已知局限（已向用户说明并接受）**：
1. 不是工业标准算法（非 AES-GCM）。对内部系统、抵御"打开数据库瞄一眼"级别足够；若要过正式安全审计或等保，需换成 `cryptography` 的 AES。
2. `data/secret.key` 一旦丢失，已存的 SMTP 密码解不开，需重新填写。文档需写明，并建议将 `secret.key` 纳入备份范围。

### 6.5 未配置邮件时的行为（B5-①②）

- **功能上静默降级**：发不出就只走站内信，不报错、不阻断
- **界面上显式提醒**：设置页顶部常驻红色横幅「邮件未配置，当前仅站内信」
- ⚠️ 此行为是**铁律**「不配置 = 行为不变」的体现 —— exe 分发到目标机器时 `.env` 通常不存在，不能让已发行的离线程序变成疯狂报错

## 7. 数据模型变更（I5，已确认）

### 7.1 改表：`users`

## 8. 日志、监控与管理界面

### 8.1 邮件状态页（I1-①②③④，全选）

| 模块 | 内容 |
|---|---|
| **① 状态概览** | 启用状态 / 发件箱地址 / SMTP 服务器（**密码打码**）/ 今日成功·失败数 / 是否处于熔断 |
| **② 发送记录列表** | 可按状态、收件人、时间筛选，分页 |
| **③ 失败清单 + 未填邮箱名单** | 失败清单支持一键重发（G7）；未填邮箱用户名单可展开（D4） |
| **④ 发送测试邮件按钮** | 发一封到当前管理员自己的邮箱，验证配置 |

> **④ 尤其重要** —— SMTP 配置是最易出错的环节（端口、SSL/TLS、授权码错一个就不通）。没有测试按钮，管理员只能"配完等明天 09:00 看有没有人收到"，排查周期被拉长一整天。

### 8.2 日志记录（I3-①）

- 位置：现有 `logs/supervision.log`（轮转 2MB×5，UTF-8）
- 内容：**只记元数据** —— 时间 / 收件人 / 邮件类型 / 成功或失败 / 错误码
- **不记**：邮件正文、SMTP 密码（硬约束 P-7）

### 8.3 发送记录保留（I2-②）

**90 天**，超期自动清理。理由：记录含邮箱地址与邮件内容，长期堆积既是隐私负担，也会让 SQLite 文件持续膨胀（备份/拷贝负担）。

### 两处口径：已由用户确认（2026-09-03）

> 以下两处 SPEC 内部存在张力，开发时先按拟定口径实现，2026-09-03 提交用户复核，
> **用户确认维持现状**。此后如需改变，按变更流程走，不要直接改代码。

1. **R-1 与 R-2 的关系** —— 确认「照发」
   - R-1 说「预警邮件收件人 = 负责人 + 所有在职管理员」，R-2 说「管理员只收每日汇总日报一封」。
   - **确认口径**：管理员**不会收到他人任务的零散邮件**（全组织逾期情况合并进 09:00 日报）；
     但若管理员本人就是某项任务的负责人，那封按人合并的提醒**照发**——他是以负责人身份
     收到，不是以管理员身份被抄送。
   - 代码依据：`enqueue_overdue_warnings()` 按 `get_overdue_tasks_by_assignee()` 遍历（纯负责人维度）；
     只有 `enqueue_daily_reports()` 用 `get_mail_subscribers(role_filter='admin')` 按角色群发。
   - 备选（未采用）：管理员一律只收日报，连自己名下任务的提醒也不发。

2. **保存配置不自动解除熔断** —— 确认「不自动」
   - 因认证失败而熔断的，改好配置并保存后**仍需点「修正后恢复发送」**。
   - 理由：熔断发生时配置页上显示的很可能就是那个错误密码，自动恢复会让
     「我改了但好像还是不行」的排查变得极难——分不清是没生效还是又失败了。
     手动点一下等于一个明确的「我确认修好了」动作。
   - 代码依据：`save_config()` 只调 `models.reset_fail_streak()`（清零连续失败计数），
     **不碰** `set_circuit_state()`；恢复是独立的 `/mail/circuit/resume` 路由。
   - 备选（未采用）：保存成功且密码有变更时自动解除熔断。
