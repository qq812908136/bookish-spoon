## 第一章 概述

### 1.1 系统简介

督办系统（`task_supervision_system`）是一套**面向小团队的轻量级任务督办/跟踪系统**。系统采用统一任务池模式，支持站内消息通知，提供清晰的任务状态流转与三层预警机制，完全离线可用，无需运维部署。

系统核心价值：**把所有任务收进一个池子，用清晰的状态流转和三层预警机制，确保每件事都有人跟、有人盯、有结果。**

### 1.2 项目背景与目标

用户是编程新手，要在组织内部搭建一套督办系统，解决四大痛点：

| 痛点编号 | 痛点描述 | 系统对策 |
|:--------:|----------|----------|
| 1 | 任务分散在各处，难以统一管理 | 统一任务池，所有任务归口管理 |
| 2 | 进度难把控，不知道任务推进到哪了 | 进度更新记录 + 任务状态流转可视化 |
| 3 | 问题滞后暴露，容易造成工作延误 | 三层预警机制，提前发现风险 |
| 4 | 缺乏闭环跟踪，事情容易不了了之 | 5 态状态机 + 强制闭环说明 |

**产品目标（3 个正交目标）**：

1. **任务收口**：将分散在各处的任务统一纳入一个任务池，实现集中管理与全局可视。
2. **进度透明**：通过状态流转、进度记录和仪表盘，让任务推进情况随时可查、可追溯。
3. **风险前置**：通过三层预警机制，在任务到期前、逾期时、长期待激活时及时预警，推动闭环。

### 1.3 适用范围与用户规模

| 项目 | 内容 |
|------|------|
| 使用规模 | 小团队 5-20 人 |
| 部署方式 | 本地部署，零配置启动 |
| 网络要求 | 完全离线可用（不依赖外部网络服务） |
| 架构预留 | 预留扩展空间，支持后续规模增长 |

### 1.4 技术栈与部署方式

| 项目 | 选型 |
|------|------|
| 后端语言 | Python |
| Web 框架 | Flask |
| 数据库 | SQLite（单文件存储） |
| 前端渲染 | Jinja2 模板渲染（服务端渲染） |
| 部署形态 | 打包为 .zip 压缩包，解压后双击 .bat 启动脚本即可运行 |
| 运行机制 | 本地服务 + SQLite 文件存储，关闭即停 |

## 第二章 角色与用户故事

### 2.1 角色定义

| 角色 | 标识 | 职责定位 |
|------|:----:|----------|
| 管理员 | admin | 任务的"督办人"，负责下发工作指令、监督整体进度、推动任务闭环、管理用户账号 |
| 任务负责人 | owner | 任务的"执行人"，负责接收指令、更新进度、推动任务完成 |

### 2.2 管理员用户故事

| 编号 | 用户故事 |
|------|----------|
| A-US-01 | 作为管理员，我希望**创建任务并指派给负责人**，以便把工作安排下去并明确责任人。 |
| A-US-02 | 作为管理员，我希望**在任务里补充工作要求**（详细描述/验收标准），以便负责人清楚知道要做成什么样。 |
| A-US-03 | 作为管理员，我希望**在线推送站内消息给负责人**（如催办、补充指令），以便及时沟通而不依赖外部工具。 |
| A-US-04 | 作为管理员，我希望**实时查看所有任务的推进情况**（按状态/负责人/优先级筛选），以便全局掌握进度、发现瓶颈。 |
| A-US-05 | 作为管理员，我希望**看到即将到期和已逾期的任务预警**，以便提前介入催办，防止工作延误。 |
| A-US-06 | 作为管理员，我希望**能编辑和关闭任何人的任务**，以便纠正错误信息或强制闭环。 |
| A-US-07 | 作为管理员，我希望**查看任务的进度更新记录**（谁在什么时候更新了什么），以便追溯执行过程。 |
| A-US-08 | 作为管理员，我希望**管理用户账号**（新增/停用负责人），以便控制系统访问权限。 |

### 2.3 任务负责人用户故事

| 编号 | 用户故事 |
|------|----------|
| O-US-01 | 作为负责人，我希望**自主新增个人任务**，以便把需要自己跟进的事情也纳入系统管理。 |
| O-US-02 | 作为负责人，我希望**查看分配给我的所有任务**（按截止日期/优先级排序），以便合理安排工作优先级。 |
| O-US-03 | 作为负责人，我希望**及时更新任务执行进度**（填写进度备注、调整状态），以便管理员掌握我的推进情况。 |
| O-US-04 | 作为负责人，我希望**收到管理员下发的工作指令和站内消息**，以便第一时间了解新任务或补充要求。 |
| O-US-05 | 作为负责人，我希望**收到任务即将到期和已逾期的提醒**，以便我主动跟进、避免遗漏。 |
| O-US-06 | 作为负责人，我希望**只能编辑自己的任务**（看不到也改不了别人的），以便数据安全、权责清晰。 |
| O-US-07 | 作为负责人，我希望**界面简洁高效**（列表为主、操作流畅），以便快速完成任务更新、不打断工作节奏。 |
| O-US-08 | 作为负责人，我希望**标记任务为已闭环并填写完成说明**，以便形成工作闭环、有据可查。 |

## 第三章 功能需求

### 需求编号规则

- 格式：`P{优先级}-{三位序号}`，如 `P0-001`
- 优先级定义：P0 = Must（必须做）、P1 = Should（应该做）、P2 = Could（可以做）
- 验收标准采用可测试的明确描述，配合"Given-When-Then"语义

---

### 3.1 P0 功能需求（必须做）

#### P0-001 用户登录与登出

**需求说明**：
系统提供基于用户名+密码的登录功能，支持登出操作。登录凭据加密存储。首次部署时通过初始化向导创建管理员账号。

**详细描述**：
- 登录页提供用户名输入框、密码输入框、登录按钮，支持回车键提交。
- 登录失败时提示"用户名或密码错误"，不区分用户名错误还是密码错误（安全考虑）。
- 登录成功后创建会话（Session），跳转至任务列表页。
- 顶部导航栏提供登出入口，登出后销毁会话，返回登录页。
- 首次启动且数据库无管理员账号时，进入初始化向导创建管理员。

**验收标准**：
1. Given 用户输入正确的用户名和密码，When 点击登录，Then 跳转至任务列表页且会话生效。
2. Given 用户输入错误的用户名或密码，When 点击登录，Then 显示"用户名或密码错误"且不跳转。
3. Given 用户已登录，When 点击登出，Then 会话销毁并返回登录页。
4. Given 首次启动且无管理员账号，When 访问系统，Then 进入初始化向导页面。

---

#### P0-002 用户角色与权限控制

**需求说明**：
系统区分 admin 和 owner 两种角色，实施基于角色的访问控制（RBAC）。admin 拥有全量权限，owner 只能管理自己的任务，但可只读查看所有人的任务列表。

**详细描述**：
- 角色枚举值：`admin`、`owner`。
- admin 权限：创建/编辑/关闭/撤销任何人的任务、重新打开闭环任务、物理删除已撤销任务、管理用户账号、配置预警参数、查看全部数据。
- owner 权限：创建个人任务、编辑自己负责的任务、更新进度、查看所有人任务列表（只读他人）、查看自己的消息。
- 权限校验在后端执行，前端仅做 UI 层面的隐藏/禁用。

**验收标准**：
1. Given owner 登录，When 尝试编辑他人任务，Then 请求被后端拒绝并返回 403。
2. Given owner 登录，When 查看任务列表，Then 能看到所有人任务但他人任务操作按钮不可用。
3. Given admin 登录，When 对任意任务执行编辑，Then 操作成功。
4. Given 未登录用户，When 直接访问任务列表 URL，Then 重定向至登录页。

#### P0-003 创建任务

**需求说明**：
用户可在统一任务池中创建新任务，填写标题、负责人、优先级、截止日期等必要字段。

**详细描述**：
- 必填字段：任务标题（≤100字）、负责人、优先级、截止日期。
- 选填字段：工作要求/描述（支持多行文本）。
- 创建人由系统自动记录为当前登录用户。
- 任务状态默认为"待启动"。
- admin 创建任务时可指派给任意负责人；owner 创建任务时负责人默认为自己且不可更改。
- 创建成功后自动生成"任务指派"站内消息发送给负责人。

**验收标准**：
1. Given admin 填写完整必填字段，When 提交创建，Then 任务写入数据库并出现在任务列表，负责人收到站内消息。
2. Given 用户未填写标题，When 提交创建，Then 提示"标题不能为空"且不创建。
3. Given owner 创建任务，When 查看负责人字段，Then 默认为自己且不可更改。
4. Given 任务创建成功，When 查看任务状态，Then 默认为"待启动"。

#### P0-004 任务列表页

**需求说明**：
系统提供统一任务列表页，支持按状态/优先级/负责人筛选、按截止日期排序、关键词搜索。

**详细描述**：
- 顶部工具栏：搜索框（按标题模糊搜索）+ 新建任务按钮。
- 筛选区：状态下拉（全部/待启动/进行中/已逾期/已闭环/已撤销）、优先级下拉、负责人下拉。
- 任务表格列：标题、负责人、优先级（带颜色标记）、状态（带颜色标签）、截止日期（逾期标红）、更新时间。
- 排序：默认按截止日期升序，可切换按优先级/更新时间排序。
- owner 默认只显示自己的任务，可在筛选中切换查看全部（只读）。
- 已逾期任务整行浅红色背景标识。
- 点击任务行从右侧滑出详情面板。

**验收标准**：
1. Given 任务列表存在多条数据，When 打开列表页，Then 默认按截止日期升序显示。
2. Given 用户选择状态筛选"已逾期"，When 应用筛选，Then 仅显示状态为"已逾期"的任务。
3. Given 用户在搜索框输入关键词，When 提交搜索，Then 显示标题包含该关键词的任务。
4. Given owner 登录，When 打开列表页，Then 默认只显示自己的任务，可切换查看全部。
5. Given 存在已逾期任务，When 查看列表，Then 该任务整行浅红色背景。

#### P0-005 任务详情查看与编辑

**需求说明**：
用户可在侧滑面板中查看任务完整信息，并在权限范围内编辑任务字段、查看进度更新记录。

**详细描述**：
- 侧滑面板从右侧滑入，覆盖约 40% 宽度，背景可点击关闭。
- 任务信息区：显示并支持编辑标题、状态、优先级、负责人、截止日期、工作要求描述。
- 状态下拉仅显示当前状态可达的合法目标状态（受状态机规则限制）。
- 进度记录时间线：按时间倒序显示所有操作记录（操作人、时间、状态变更、备注）。
- 权限控制：owner 只能编辑自己负责的任务；admin 可编辑所有任务。

**验收标准**：
1. Given 用户点击任务行，When 面板滑出，Then 显示任务完整信息和进度记录时间线。
2. Given owner 查看他人任务，When 查看编辑控件，Then 所有编辑控件为只读/禁用状态。
3. Given 用户切换状态下拉，When 查看可选项，Then 仅显示状态机允许的目标状态。
4. Given 点击面板外背景区域，When 触发关闭，Then 面板滑出消失。

#### P0-006 任务状态流转

**需求说明**：
系统实现 5 态状态机（待启动/进行中/已逾期/已闭环/已撤销），支持手动流转与超期自动转"已逾期"。

**详细描述**：
- 5 个状态：待启动（S1）、进行中（S2）、已逾期（S3）、已闭环（S4）、已撤销（S5）。
- 系统自动触发：当"待启动"或"进行中"任务超过截止日期，自动变为"已逾期"。
- 手动流转遵循状态转换矩阵（见第四章）。
- 转为"已闭环"时必须填写完成说明。
- "已闭环"仅管理员可重新打开至"进行中"。
- "已撤销"可由管理员重新激活至"待启动"。

**验收标准**：
1. Given 任务处于"待启动"且当前时间超过截止日期，When 系统定时扫描，Then 任务自动变为"已逾期"并触发预警。
2. Given 用户标记任务为"已闭环"，When 未填写完成说明，Then 提示"请填写完成说明"且不闭环。

#### P0-009 三层预警机制

**需求说明**：
系统实现三层预警（即将到期3天/已逾期/长期待激活7天），自动触发站内消息通知。

**详细描述**：
- 第一层（即将到期预警）：截止日期前 3 天（含当天），任务为"待启动"或"进行中"，通知负责人。每天 1 次（建议每日 09:00 扫描）。
- 第二层（已逾期预警）：任务超期未闭环，状态已变"已逾期"，通知负责人 + 管理员。触发时 1 次 + 每日提醒 1 次。
- 第三层（长期待激活预警）：任务创建后超 7 天仍"待启动"，通知负责人 + 管理员。每 7 天提醒 1 次。
- 多层预警可叠加，系统合并为一条通知避免消息轰炸。
- 任务进入"已闭环"或"已撤销"后，该任务所有预警自动停止。
- 预警天数（3天/7天）可由管理员配置，默认 3 天 / 7 天。

**验收标准**：
1. Given 任务距截止日期 3 天且状态为"进行中"，When 系统每日扫描，Then 负责人收到"即将到期预警"消息。
2. Given 任务超过截止日期，When 系统扫描检测到，Then 任务变"已逾期"且负责人+管理员收到"已逾期预警"。
3. Given 任务创建后 7 天仍为"待启动"，When 系统扫描检测到，Then 负责人+管理员收到"长期待激活预警"。
4. Given 任务同时满足多层预警条件，When 系统扫描，Then 合并为一条通知发送。
5. Given 任务进入"已闭环"，When 系统扫描，Then 该任务不再触发任何预警。

## 第四章 业务流程说明

### 4.1 任务状态机（5 态流转）

#### 4.1.1 状态定义

| 状态码 | 状态名称 | 含义 | 颜色标识 |
|:------:|----------|------|----------|
| S1 | **待启动** | 任务已创建但尚未开始执行，负责人还没动工 | 灰色 |
| S2 | **进行中** | 任务正在推进中，负责人已开始执行 | 蓝色 |
| S3 | **已逾期** | 超过截止日期仍未闭环。**独立状态**（非标签），表示任务已出现风险，需重点关注 | 红色 |
| S4 | **已闭环** | 任务已完成，形成工作闭环。终态之一 | 绿色 |
| S5 | **已撤销** | 任务不再需要执行（取消/作废）。终态之一 | 深灰色（删除线样式） |

#### 4.1.2 状态转换矩阵

> 行 = 当前状态，列 = 目标状态。✅ = 允许转换，❌ = 不允许，🔄 = 系统自动触发。

| 当前＼目标 | 待启动 | 进行中 | 已逾期 | 已闭环 | 已撤销 |
|-----------|:------:|:------:|:------:|:------:|:------:|
| **待启动** | — | ✅ 开始执行 | 🔄 超期自动触发 | ✅ 直接闭环 | ✅ 撤销 |
| **进行中** | ❌ | — | 🔄 超期自动触发 | ✅ 完成闭环 | ✅ 撤销 |
| **已逾期** | ❌ | ✅ 恢复推进 | — | ✅ 闭环（逾期完成） | ✅ 撤销 |
| **已闭环** | ❌ | ✅ 管理员重新打开 | ❌ | — | ❌ |
| **已撤销** | ✅ 管理员重新激活 | ❌ | ❌ | ❌ | — |

#### 4.1.3 流转规则说明

1. **待启动 → 进行中**：负责人点击"开始"，或管理员推送消息后负责人响应。
2. **进行中 → 已闭环**：负责人/管理员标记完成，**必须填写完成说明**。
3. **超期自动 → 已逾期**：系统定时检查（建议每 5 分钟扫描一次），将超期未闭环的"待启动"和"进行中"任务自动置为"已逾期"，并触发第二层预警。
4. **已逾期 → 进行中**：负责人更新进度后可手动改回，表示"我知道逾期了，正在推进"。
5. **已闭环 → 进行中**：**仅管理员可操作**，用于闭环后发现需要返工的情况。
6. **已撤销 → 待启动**：**仅管理员可操作**，用于误撤销后恢复。

#### 4.1.4 自动逾期触发流程

```
系统定时扫描（每5分钟）
        │
        ▼
遍历所有"待启动"和"进行中"任务
        │
        ▼
   当前时间 > 截止日期？
    ├── 是 ──▶ 状态变更为"已逾期" ──▶ 触发第二层预警 ──▶ 记录状态变更日志
    └── 否 ──▶ 跳过，继续下一个
```

### 4.2 三层预警机制

#### 4.2.1 预警层级定义

| 层级 | 预警名称 | 触发条件 | 提醒对象 | 提醒方式 | 频率 |
|:----:|----------|----------|----------|----------|------|
| **第一层** | 即将到期预警 | 任务截止日期前 **3 天**（含当天），且任务状态为"待启动"或"进行中" | 任务负责人 | 站内消息（红点+通知列表） | 每天 1 次（建议每日 09:00 扫描） |
| **第二层** | 已逾期预警 | 任务超过截止日期仍未闭环，状态已自动变为"已逾期" | 任务负责人 **+ 管理员** | 站内消息（红点+通知列表，标记"逾期"高亮） | 触发时 1 次 + 每日提醒 1 次（建议每日 09:00） |
| **第三层** | 长期待激活预警 | 任务创建后超过 **7 天**仍未启动（状态仍为"待启动"） | 任务负责人 **+ 管理员** | 站内消息（红点+通知列表，标记"待激活"） | 每 7 天提醒 1 次 |

#### 4.2.2 预警规则补充说明

- **多层叠加合并**：一个任务可能同时触发多层预警（如创建后 7 天未启动 + 距截止 3 天），系统会合并为一条通知，避免消息轰炸。
- **参数可配置**：预警天数（3 天 / 7 天）可在管理员设置页调整，默认值如上。
- **通知内容**：预警触发后，通知列表显示任务标题、预警类型、触发时间，点击可直接跳转任务详情。
- **预警停止**：任务进入"已闭环"或"已撤销"后，该任务的所有预警自动停止。

#### 4.2.3 预警触发流程

```
每日定时扫描（建议09:00）
        │
        ▼
   遍历所有活跃任务（非终态）
        │
        ├── 第一层检查：距截止日期≤3天且为待启动/进行中？
        │       └── 是 ──▶ 记录即将到期预警
        │
        ├── 第二层检查：已超过截止日期？
        │       └── 是 ──▶ 状态自动转"已逾期" ──▶ 记录已逾期预警
        │
        ├── 第三层检查：创建超7天且仍为"待启动"？
        │       └── 是 ──▶ 记录长期待激活预警
        │
        ▼
   合并同一任务的多个预警为一条通知
        │
        ▼
   发送站内消息给对应提醒对象
```

### 4.3 权限模型

#### 4.3.1 权限矩阵

| 操作 | admin（管理员） | owner（任务负责人） |
|------|:---------------:|:------------------:|
| 登录系统 | ✅ | ✅ |
| 创建任务 | ✅（可指派任意人） | ✅（负责人默认为自己） |
| 查看任务列表 | ✅ 全部任务 | ✅ 全部任务（他人只读） |
| 编辑任务字段 | ✅ 所有任务 | ✅ 仅自己负责的任务 |
| 更新任务进度 | ✅ 所有任务 | ✅ 仅自己负责的任务 |
| 变更任务状态 | ✅ 所有任务 | ✅ 仅自己负责的任务（受状态机限制） |
| 重新打开已闭环任务 | ✅ | ❌ |
| 重新激活已撤销任务 | ✅ | ❌ |
| 物理删除已撤销任务 | ✅ | ❌ |
| 撤销任务 | ✅ | ✅ 仅自己负责的任务 |
| 用户管理（新增/停用/重置） | ✅ | ❌ |
| 预警参数配置 | ✅ | ❌ |
| 查看仪表盘 | ✅ | ✅ |
| 查看站内消息 | ✅（自己收到的） | ✅（自己收到的） |
| 个人设置（改密码/显示名） | ✅ | ✅ |
| 导出任务 | ✅ | ✅ |
| 批量操作 | ✅ | ❌ 批量指派；部分批量状态变更受限 |

#### 4.3.2 权限控制原则

1. **后端强制校验**：所有权限校验在后端执行，前端仅做 UI 层面的隐藏/禁用（防止绕过）。
2. **数据隔离 vs 信息透明**：owner 可查看所有人任务列表（信息透明有助于协作），但编辑权限严格限制为自己负责的任务。
3. **终态操作收敛**：重新打开闭环、重新激活撤销、物理删除等高风险操作仅限管理员。
4. **消息按收件人隔离**：每个用户只能查看发送给自己的站内消息。

### 4.4 任务生命周期

#### 4.4.1 完整生命周期流程

```
【创建阶段】
管理员/负责人创建任务 ──▶ 填写标题、负责人、优先级、截止日期 ──▶ 任务进入"待启动"
        │                                                         │
        │                                           系统发送"任务指派"消息给负责人
        │                                                         │
        ▼                                                         ▼
【指派与启动】                                              负责人收到通知
负责人查看任务 ──▶ 点击"开始" ──▶ 状态变"进行中" ──▶ 记录进度更新日志
        │
        │
        ▼
【推进阶段】
负责人定期更新进度 ──▶ 填写进度备注 ──▶ 系统记录进度日志 ──▶ 管理员可查看进度
        │
        ├── 正常推进 ──▶ 距截止3天 ──▶ 第一层预警（通知负责人）
        │
        ├── 超期未完成 ──▶ 系统自动转"已逾期" ──▶ 第二层预警（通知负责人+管理员）
        │                                       │
        │                               负责人可改回"进行中"继续推进
        │
        ├── 创建后7天未启动 ──▶ 第三层预警（通知负责人+管理员）
        │
        ▼
【闭环/撤销阶段】
        ├── 任务完成 ──▶ 标记"已闭环" ──▶ 必填完成说明 ──▶ 记录闭环时间 ──▶ 停止所有预警
        │
        ├── 任务不再需要 ──▶ 标记"已撤销" ──▶ 停止所有预警
        │
        ▼
【终态后纠错（仅管理员）】
        ├── 已闭环需返工 ──▶ 管理员重新打开 ──▶ 状态变"进行中" ──▶ 重新进入推进阶段
        │
        ├── 已撤销误操作 ──▶ 管理员重新激活 ──▶ 状态变"待启动" ──▶ 重新进入启动阶段
        │
        └── 已撤销需彻底删除 ──▶ 管理员物理删除 ──▶ 从数据库移除（不可恢复）
```

| 节点 | 触发方 | 动作 | 系统响应 |
|------|--------|------|----------|
| 创建 | admin/owner | 填写并提交任务 | 入库、发指派消息 |
| 启动 | 负责人 | 点击"开始" | 状态→进行中、记日志 |
| 进度更新 | 负责人/admin | 填写备注/改状态 | 记日志、发状态变更消息 |
| 即将到期预警 | 系统 | 每日扫描 | 发第一层预警消息 |
| 自动逾期 | 系统 | 每5分钟扫描 | 状态→已逾期、发第二层预警 |
| 长期待激活预警 | 系统 | 每日扫描 | 发第三层预警消息 |
| 闭环 | 负责人/admin | 标记完成+填说明 | 状态→已闭环、记闭环时间、停预警 |
| 撤销 | 负责人/admin | 标记撤销 | 状态→已撤销、停预警 |
| 重新打开 | admin | 重开闭环 | 状态→进行中、记日志 |
| 重新激活 | admin | 激活撤销 | 状态→待启动、记日志 |
| 物理删除 | admin | 删除已撤销任务 | 从数据库移除 |

## 第十章 V2 迭代增补

> **增补日期**：2026-08-28（V2 迭代开发完成后文档同步）
> **增补依据**：`iteration-v2-design.md`（Q1–Q9 已确认）+ V2 交付代码（4 批次：UI 底座 / 数据库迁移+仪表盘 / 抽屉交互 / 功能补全）
> **视觉与交互基准**：`督办仓-离线版.html` 单页模板，转译为 Jinja2 + 原生 JS（不引入前端框架与 CDN 依赖）

### 10.1 迭代概述

V2 在**完整保留 V1 全部功能**（批量操作、CSV 导出、用户管理、三层预警、初始化向导、PyInstaller 离线打包等，对应差异分析清单 C1–C12）的前提下，完成两类升级：

1. **视觉与交互重做**：左侧边栏 → 顶栏导航 + 抽屉交互体系，新增深色模式；
2. **功能补全**：任务新字段、过程证据、阻塞记录、闭环矩阵、推送提醒。

### 10.2 新增功能清单

#### V2-01 任务字段扩展：进度% / 风险点 / 协同方

> **用户价值**：负责人用一句进度数字 + 风险说明即可汇报进展，管理员不必逐条追问"推进到哪了、卡在哪"。

**功能点**：
- `tasks` 表新增 3 字段：`progress_percent`（进度%，整数 0–100）、`risk_note`（风险点，文本）、`collaborators`（协同方，文本，逗号分隔多人）
- 新建任务表单、编辑任务表单、任务详情独立页、任务详情抽屉（含行内编辑）均支持这 3 个字段
- 校验规则：进度必须是 0–100 的整数；风险点/协同方文本上限 500 字
- 抽屉详情页签顶部展示进度条 + 百分比，行内修改进度%后进度条即时联动刷新
- 编辑表单向后兼容：旧表单未携带这 3 个字段时保留原值，不清零

#### V2-02 过程证据与阻塞记录（新表）

> **用户价值**：任务推进中的关键凭据（文字说明/链接/文件名）和卡点（阻塞）有了专门的家，过程可追溯、卡点不沉没。

**功能点**：
- 新表 `evidence`（过程证据）：类型三选一 text（文字）/ link（链接）/ file（文件名，不真正上传文件）
- 新表 `blockers`（阻塞记录）：状态两态 open（待解决）/ resolved（已解决）
- 添加入口：任务详情抽屉"过程证据""阻塞记录"两个页签内的添加表单，AJAX 提交
- 权限：owner 可为自己的任务添加；admin 可为所有任务添加；阻塞"标记解决"仅 admin 或记录创建者本人
- 内容上限 500 字；所有增删/解决操作自动写入 `progress_logs` 时间线留痕（纯备注型日志，状态字段为空）

#### V2-03 抽屉交互体系（3 个抽屉）

> **用户价值**：查看和更新任务不再整页跳转，信息在原位滑入呈现，操作路径从"点开→跳页→返回"缩短为"点行→抽屉→关闭"。

**功能点**：
- **任务详情抽屉**：任务列表行点击（含仪表盘焦点列表）→ 右侧滑入抽屉，含"详情 / 过程证据 / 阻塞记录"3 个页签；详情页签支持全字段行内编辑、状态流转、进度时间线
- **Owner 抽屉**：仪表盘闭环矩阵点击负责人名字 → 该负责人名下任务列表抽屉（最多 50 条，按截止日期升序）
- **消息抽屉**：顶栏铃铛点击 → 最近 50 条消息抽屉，支持类型筛选、单条已读、全部已读；点击消息 → 标记已读 + 打开关联任务详情抽屉
- 原 `/messages` 独立消息中心页**移除**，旧链接 301 跳转到 `/dashboard`
- 原任务详情独立页 `/tasks/<id>` **保留**，用于消息跳转降级、JS 失效降级、浏览器直链三种场景
- 交互细节：ESC / 点击遮罩 / 关闭按钮均可关闭；操作成功后抽屉内容自动刷新（重新拉取片段，权限由服务端重算）

#### V2-04 仪表盘 V2

> **用户价值**：管理员一眼看清"总量—状态—谁在拖后腿"，按时间范围切换统计口径，督办例会的数据信手拈来。

**功能点**：
- 6 张可点击统计卡：任务总数 / 待启动 / 进行中 / 已逾期 / 已闭环 / 闭环率（点击跳转任务列表对应筛选）
- **今日督办焦点**列表：非终态任务按"已逾期 > 进行中 > 待启动"排序、同状态内按到期日升序，最多 20 条；当前用户负责的任务带"我的"标记
- **任务闭环矩阵**：列依次为 **负责人 / 任务数 / 待启动 / 进行中 / 已逾期 / 已闭环 / 已撤销 / 闭环率**（共 8 列，状态列使用完整状态名，不用缩写），按任务数降序，每页 8 人分页；点负责人名字开 Owner 抽屉，点数字跳任务列表带筛选
- **时间范围筛选**：全部 / 本年 / 本季 / 本月 / 本周下拉，按任务创建时间过滤，仅作用于仪表盘（统计卡 + 焦点 + 矩阵）
- 闭环率口径（Q9 已确认）：`closed ÷ (总数 − 已撤销)`，分母为 0 时显示"—"
- 原"我的待办"区块并入焦点列表；原 4 卡统计页由本页替代

#### V2-05 行内编辑接口

> **用户价值**：改一个字段不再进入整页编辑表单，点击字段、输入、回车即保存，督办更新像改表格一样轻。

**功能点**：
- 接口：`POST /tasks/<id>/field`（JSON 请求/响应）
- 字段白名单 8 个：`title` / `description` / `priority` / `due_date` / `progress_percent` / `risk_note` / `collaborators` / `assignee`
- 权限：复用 `can_edit_task`（admin 全部可改；owner 仅自己的任务，他人任务字段只读展示）；`assignee`（改派）额外仅 admin 可操作，改派成功自动给新负责人发站内通知
- 交互：点击字段值原位变输入框（文本/数字/日期/下拉/多行自适应），失焦或回车保存，ESC 取消；保存结果 Toast 反馈
- 服务端逐字段校验（标题非空且 ≤100 字、优先级枚举、日期 YYYY-MM-DD、进度 0–100、负责人存在且启用）

#### V2-06 证据 / 阻塞管理权限（删除仅 admin）

> **用户价值**：留痕数据不会被误删——负责人可自助记录，但销毁凭据的权限收归管理员，保证督办过程记录的严肃性。

**功能点**：
- 删除接口：`POST /tasks/<id>/evidence/<eid>/delete`、`POST /tasks/<id>/blockers/<bid>/delete`，**仅 admin**
- 删除前二次确认（浏览器 confirm）；AJAX 调用返回 JSON，普通 POST 重定向回详情页（双通道兼容）
- 删除操作同样写入进度时间线留痕；证据/阻塞必须属于对应任务，跨任务 ID 返回 404

#### V2-07 推送提醒

> **用户价值**：管理员在矩阵里发现某人逾期堆积，点一下"推送提醒"即可定向催办，不必切换到发消息页手写内容。

**功能点**：
- 接口：`POST /tasks/remind`（admin 专用），参数 `task_id`（提醒某任务的负责人，消息带任务标题/状态/截止日）或 `owner_id`（泛化提醒某负责人名下任务）二选一
- 实现：复用站内信系统，给目标负责人发一条 `admin_directive` 类型消息（Q8 已确认，不做邮件通道）
- 入口：Owner 抽屉顶部"推送提醒"按钮（仅 admin 可见）；不能给自己推送

#### V2-08 视觉体系重做（UI 底座）

> **用户价值**：界面从"能用"升级到"好用好看"：现代配色、状态一眼可辨、深夜加班有深色模式。

**功能点**：
- 布局：左侧边栏 → 顶部固定导航栏（概览/任务/设置/用户管理*/系统设置*，* 仅 admin），移动端收进汉堡菜单
- 视觉规范对齐模板：品牌蓝 #2563eb、卡片圆角 12px + 轻阴影 + hover 上浮、药丸状态标签（浅底深字 + 色点）、Toast 右下角通知（flash 消息自动转发为 Toast，flash 保留兜底）
- 状态徽章体系：`st-<status>` 类（st-pending 灰 / st-in_progress 琥珀 / st-overdue 红 / st-closed 绿 / st-cancelled 浅灰）；优先级彩色药丸（urgent 红 / high 橙 / medium 蓝 / low 灰），保留四级优先级（Q7）
- **深色模式**：顶栏一键切换，`html.dark` 切换全套 CSS 变量，偏好存 localStorage（默认浅色）
- 图标：Lucide SVG 以 Jinja2 宏（`templates/macros/icons.html`，约 25 个图标）内联输出，零外部依赖；字体走系统字体栈，不内嵌字体文件
- 登录页重做：左品牌介绍区 + 右登录卡，字段级错误提示（用户名/密码分开报错）、"记住我"用户名 cookie（30 天）、密码可见切换
- 技术约束不变：仍是 Flask + Jinja2 + 原生 JS + 单 CSS 文件，无构建工具，PyInstaller 离线打包零风险

| 仪表盘统计 | 4 静态统计卡 + 状态分布 + 我的待办 | 6 可点击统计卡 + 今日督办焦点 + 任务闭环矩阵 + 时间范围筛选 |
| 导航 | 左侧边栏（emoji 图标） | 顶部固定导航栏（Lucide 图标）+ 铃铛 + 深色切换 |
| 任务列表批量操作 | 工具栏按钮 | 功能不变，选中后底部浮出操作条（模板风格） |
| 登录 | 单卡片、通用错误提示 | 左右分栏、字段级错误（空字段 400 / 凭据错误 401）、记住用户名、密码可见切换 |

### 10.5 兼容性说明

1. **老数据库自动升级**：V1 数据库启动时自动迁移（建新表 IF NOT EXISTS + `PRAGMA table_info` 检查缺列后 `ALTER TABLE ADD COLUMN`），秒级完成、数据不丢、可重复执行（幂等）；迁移异常仅记日志，不中断启动。
2. **旧链接兼容**：`/messages` 301 跳转 `/dashboard`，不产生 404；`/messages/send`、`/messages/read-all`、`/messages/unread-count` 等路由全部保留，由抽屉继续调用。
3. **登录接口**：登录失败返回 **401**（用户名或密码错误，不暴露账号是否存在）；用户名/密码为空返回 400 并定位到具体字段。
4. **V1 功能全量保留**：批量操作、CSV 导出（含中文文件名编码）、用户管理、系统设置、三层预警引擎、初始化向导、局域网部署与 PyInstaller 打包均正常，相关测试用例保留（消息中心页用例改为断言 301 跳转）。
5. **编辑表单向后兼容**：旧表单/客户端提交不含 3 个新字段时，字段保留原值不清零。

### 10.6 非目标重申（V2 明确不做）

以下为 V2 迭代范围外事项（详见 `iteration-v2-design.md` §9），避免误解为已实现：

1. **真实文件上传**：file 类证据仅记录文件名/可选链接，不上传文件本体
2. **邮件通道**：推送提醒仅走站内信（Q8 已确认）
3. **P0/P1/P2 三级优先级改造**：保留现有 urgent/high/medium/low 四级（Q7 已确认）
4. **前后端分离 / SPA 改造**：仍是 Flask + Jinja2 服务端渲染 + 原生 JS
5. **部门、来源会议、会议日期、任务资产 ID、引用原话字段**：Q1 已确认不新增
