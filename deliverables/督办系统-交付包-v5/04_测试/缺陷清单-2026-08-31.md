### DEF-002 全站缺少 CSRF 防护，写操作可被跨站请求伪造 　✅ 已修复（2026-09-01）
- **位置**：全局（所有 `methods=['POST']` 路由均无 CSRF token）；`routes/*.py`、`auth.py`
- **类别**：安全
- **严重程度**：一般
- **状态**：✅ **已修复**（2026-09-01）。修复方案与验收记录见 `docs/上线前待办.md` 的 DEF-002 章节。下文「描述 / 复现步骤 / 影响范围」为**修复前的原始记录**，保留作为历史追溯依据。
- **修复要点**：
  1. 新增 `src/csrf.py`：令牌 = `过期时间戳 + HMAC-SHA256(会话密钥, 时间戳)`，校验时现算并做常量时间比较；
  2. `app.py` 的 `before_request` 统一校验所有非安全方法 —— 放在全局钩子而非逐路由装饰器，**新写的 POST 路由默认就受保护**；
  3. 上下文处理器注入 `csrf_token`，21 个 `method="POST"` 表单（跨 10 个模板）全部带上 hidden 字段；
  4. `base.html` 输出 `<meta name="csrf-token">`，`main.js` 用统一的 `csrfHeaders()` 为 8 处写请求注入 `X-CSRF-Token` 头；
  5. 登录成功时轮换会话密钥，登录前签发的令牌作废；
  6. 配置开关 `CSRF_ENABLED`（默认 true）与 `CSRF_TOKEN_MAX_AGE`（默认 24 小时）；
  7. 新增 `TestCSRF` 16 项用例，其中 3 项为防回归（遍历 url_map 的 24 条写路由 / 扫描模板的 21 个表单 / 扫描 main.js 的 8 处 AJAX）。
- **为何自研而不引入 Flask-WTF**：新增 Python 依赖要同时改 requirements.txt、PyInstaller spec 的 hiddenimports、托管解释器安装、重新打包 exe 四处；核心逻辑不到 150 行，自己写更可控，也不增加离线程序体积。
- **遗留提示**：
  - `SameSite=Lax` 保留作为**第二道防线**，两层互不依赖；
  - 页面停留超过 `CSRF_TOKEN_MAX_AGE`（默认 24 小时）后提交会提示刷新，可按需调大；
  - `csrf_exempt` 仅供确实无副作用的内部接口，写操作路由一律不要加。
- **描述（原始记录）**：grep 确认代码中无任何 `csrf` / `CSRFProtect` / `FlaskForm` / `WTF` 防护。登录、建任务、改状态、删任务、发消息、重置密码等所有状态变更均为无 token 的 POST。已登录用户访问恶意页面时，攻击者可借其身份发起伪造请求。
- **复现步骤**：
  1. 受害者登录系统并保持会话；
  2. 访问攻击者构造的网页，内含自动提交的表单（action 指向 `/tasks/<id>/delete` 或 `/users/<id>/reset-password` 等）；
  3. 浏览器携带受害者 Cookie 发出请求 → 以受害者权限执行操作。
- **影响范围**：所有已登录用户；可触发改密码、删除任务、批量改状态、推送消息等敏感操作。
- **修复建议**：
  - 引入 `Flask-WTF` 的 `CSRFProtect`（统一对所有 POST/PUT/DELETE 校验）；
  - 或统一在 `main.js` 的 AJAX 请求与表单中注入并校验同源 token（服务端用 `session` 存储 token 比对）；
  - 对 `unread-count` 之外的写接口均须覆盖。

### DEF-003 写操作未走全局写锁，SQLite 并发写入可能报 "database is locked" 致 500
- **位置**：`db.py:56-80`（`transaction()` 有 `_lock`，但 `db.py:93/106/121` 的 `query/query_one/execute` 不走锁）；调用方 `models.py` 多处及 `routes/task_routes.py`、`warning_engine.py` 直接使用 `db.execute`
- **类别**：健壮性
- **严重程度**：一般
- **描述**：`db.execute` 立即提交且不加全局锁，而 `check_same_thread=False` + 多线程连接意味着请求线程与后台调度线程（逾期扫描/预警扫描）各自持有独立连接并发写同一 SQLite 文件。Flask 开发服务器默认 `threaded=True`，并发请求也会各自写库。写冲突时 SQLite 抛出 `SQLITE_BUSY`，未被捕获即表现为 500。
- **复现步骤**：
  1. 启动服务（含后台预警/逾期线程）；
  2. 用多线程/并发工具同时触发写操作（如连续提交多个任务、同时标记消息已读 + 后台 09:00 预警扫描落库）；
  3. 观察偶发 500，服务端日志出现 `database is locked`。
- **影响范围**：高并发或后台扫描与用户操作重叠时，部分请求随机失败；数据一致性偶发受损。
- **修复建议**：
  - 所有写操作统一经 `db.transaction()`（已带 `_lock`），不要用裸 `db.execute` 提交；
  - 或将 `db.execute` 也纳入全局锁；
  - 启用 SQLite WAL 模式（`PRAGMA journal_mode=WAL`）提升并发读写能力；
  - 连接设置合理的 `busy_timeout`（如 5–10s）。

### DEF-005 登录无频率限制/锁定，弱口令易被暴力破解 　✅ 已修复（2026-08-31）
- **位置**：`src/auth.py`（`do_login` 限流 + `check_password_strength`）、`src/config.py`（4 个新配置项）、4 个设置密码的路由
- **类别**：安全
- **严重程度**：一般
- **状态**：✅ **已修复**（2026-08-31）。修复方案与验收记录见 `docs/上线前待办.md` 的 DEF-005 章节。下文「描述 / 复现步骤 / 影响范围」为**修复前的原始记录**，保留作为历史追溯依据。
- **修复要点**：
  1. **登录失败限流**：按「客户端 IP + 用户名」组合计数，连续失败 5 次（`LOGIN_MAX_ATTEMPTS`）锁定 15 分钟（`LOGIN_LOCKOUT_MINUTES`）；锁定期内**即使密码正确也拒绝**；到期自动解锁，登录成功立即清零。
  2. **弱口令拦截**：新增 `check_password_strength()`，规则为长度 ≥8（可配）、禁纯数字、禁纯字母、常见弱口令黑名单（比较不区分大小写）、不得与用户名相同。
  3. **覆盖全部 4 个入口**：初始化向导、新建用户、重置密码、个人改密码 —— 修复前仅初始化向导有一句 `len >= 6`。
  4. **不追溯已有账号**：历史遗留的 6 位弱密码账号仍可登录，只在下次改密码时才要求达标。
  5. **登录审计日志**：失败（含原因与剩余次数）与成功均记入 `logs/supervision.log`。
- **遗留项**：演示库里的 `admin/admin123`、`owner/123456` 本身仍是弱口令（限流只能挡爆破、挡不住已知弱口令）。正式上线前需改掉或重置数据后重新建号。
- **描述**：登录接口对失败次数无任何限制（无锁定、无验证码、无速率限制），可无限次尝试。演示数据使用弱口令（管理员 `admin123`、负责人 `123456`），若未被清理即随产品交付，极易被爆破。
- **复现步骤**：
  1. 用脚本对 `/login` 循环提交常见口令字典；
  2. 无任何锁定/延迟/拦截，直至命中正确口令。
- **影响范围**：账号安全；尤其管理员账号被破解后配合 DEF-001 可直接接管。
- **修复建议**：
  - 增加登录失败计数与锁定（如 5 次失败锁定 15 分钟）或滑动速率限制；
  - 交付前清理演示账号与弱口令，强制首次登录改密；
  - 口令复杂度校验（当前 `setup`/`user_new` 仅要求 ≥6 位，过弱，建议 ≥8 位含复杂度）。

### DEF-015 新建任务页「截止日期」选中后占位/日期值显示异常
- **位置**：`templates/tasks/form.html`（日期输入框占位实现）、`static/css/main.css`（原 `input[type=date]{color:transparent}` + `.date-input-wrapper::after` 伪元素回写 `data-display-value` 的 hack）、`static/js/main.js`（`initDatePlaceholder`）
- **类别**：逻辑/UI

  3. 观察输入框：仍显示占位文字，或日期值与占位文字重叠，无法清晰确认所选值。

  3. 逾期扫描中 `datetime.strptime` 抛异常被吞（warning_engine 有 try/except），该任务预警被静默跳过。
- **影响范围**：单条任务数据质量；可能导致该任务永不预警/逾期判断异常。
- **修复建议**：在 `task_new`/`task_edit` 中对 `due_date` 套用与 `task_field` 相同的 `_DATE_RE` 校验，非法则报错回显。

### DEF-007 `models.update_task` 用 f-string 拼接字段名，存在潜在 SQL 注入隐患
- **位置**：`models.py:399-415`（`set_clauses = [f"{key} = ?" for key in fields]`，再 `UPDATE tasks SET {', '.join(set_clauses)}`）
- **类别**：安全（潜在）
- **严重程度**：轻微
- **描述**：当前所有调用方（`task_field` 用白名单 `FIELD_WHITELIST`、`task_edit`/`task_batch`/`task_new` 均传硬编码 key）传入的字段名均可信，目前不可注入。但该接口契约未强制白名单，一旦未来某处把 `request.form` 的 key 直接透传为 `**fields`，即构成 SQL 注入。
- **复现步骤**：待确认 —— 需确认是否存在将用户可控字典直接 `**` 展开传入 `update_task` 的调用（当前审查未发现，但属架构性薄弱点）。
- **影响范围**：若存在不当调用，可篡改任意字段或执行注入。
- **修复建议**：在函数内部对 `fields` 的 key 做白名单校验（复用 `FIELD_WHITELIST` 思路），拒绝非预期字段名；或将字段名映射为固定枚举。

### DEF-008 任务导出一次性加载全部匹配任务进内存
- **位置**：`routes/task_routes.py:406`（`models.get_tasks(filters, page=1, per_page=100000)`）
- **类别**：健壮性/性能
- **严重程度**：轻微
- **描述**：`/tasks/export` 为导出"当前筛选条件下全部任务"，使用 `per_page=100000` 一次取回所有行并全部写入单个 xlsx 工作簿。任务量极大时内存与响应时间不可控。
- **复现步骤**：
  1. 系统内存在数万条任务；
  2. 访问 `/tasks/export`；
  3. 服务端内存骤增，响应缓慢甚至超时。
- **影响范围**：大数据量部署的导出功能可用性。
- **修复建议**：改为流式写入（openpyxl 的 `WriteOnlyWorkbook`）或分页批量拼接；或限制单次导出上限并提示。

### DEF-009 分页越界未归正，超页显示空列表
- **位置**：`routes/task_routes.py:78-79`（`total_pages = max(1, ...)` 已算，但 `page` 未 clamp 到 `total_pages`）
- **类别**：逻辑
- **严重程度**：轻微
- **描述**：当用户手动构造 `?page=9999` 且总页数较少时，`get_tasks` 的 `offset=(page-1)*per_page` 超出总量，返回空列表并渲染空白页，而非回退到末页。
- **复现步骤**：
  1. 任务列表仅 1 页；
  2. 访问 `/tasks?page=9999`；
  3. 页面显示"无任务"。
- **影响范围**：仅展示异常，无数据风险。
- **修复建议**：`page = min(max(1, page), total_pages)` 后再查询。

### DEF-010 `task_remind` 对 `task_id`/`owner_id` 直接 `int()` 未捕获异常
- **位置**：`routes/task_routes.py:1094`（`int(task_id)`）、`routes/task_routes.py:1104`（`int(owner_id)`）
- **类别**：健壮性
- **严重程度**：轻微
- **描述**：参数来源包含 `request.args`（查询串），若传入非数字（如 `task_id=abc`）会抛 `ValueError` 且未被捕获，导致 500 而非 400。
- **复现步骤**：
  1. 以管理员身份 POST/GET `/tasks/remind?task_id=abc`；
  2. 服务端 500。
- **影响范围**：单请求异常，无安全风险。
- **修复建议**：用 `try/except ValueError` 包裹，非法参数返回 400 JSON。

### DEF-011 初始化向导无并发保护，竞态下可创建多个管理员
- **位置**：`routes/auth_routes.py:96-134`（`setup` 先 `has_admin()` 判断再 `create_user`，两步非原子）
- **类别**：逻辑
- **严重程度**：轻微
- **描述**：`/setup` 的"是否已有管理员"检查与"创建管理员"之间无锁，两个并发请求可能都通过检查并各创建一个管理员账号（虽 `username` 唯一约束会拦住同名，但不同用户名即可绕过）。
- **复现步骤**：待确认 —— 需确认实际部署是否会出现并发初始化（个人单机场景概率低，但多人在同一台初始化向导期存在理论风险）。
- **影响范围**：可能产生非预期的管理员账号。
- **修复建议**：创建管理员时加全局锁或用唯一约束保证单管理员；或在 `create_user` 后再次校验。

### DEF-012 生产环境启用了模板自动重载
- **位置**：`app.py:41`（`app.config['TEMPLATES_AUTO_RELOAD'] = True`）
- **类别**：部署/性能
- **严重程度**：轻微
- **描述**：模板自动重载用于开发期，生产/离线运行时会带来额外的模板重新编译开销，并可能在文件系统变动时表现异常。
- **复现步骤**：无需复现，属配置项。
- **影响范围**：轻微性能与可预期性。
- **修复建议**：根据 `config.DEBUG` 决定是否开启（如 `TEMPLATES_AUTO_RELOAD = config.DEBUG`）。

### DEF-013 "记住用户名" Cookie 明文存储用户名
- **位置**：`routes/auth_routes.py:67`（`resp.set_cookie('remember_username', username, max_age=30*24*3600)`）
- **类别**：安全（隐私）
- **严重程度**：轻微
- **描述**：登录名以明文存入客户端 Cookie（非 HttpOnly 风险低，但用户名本身属半敏感信息），任何可读取该设备的人都能看到上次登录账号。
- **复现步骤**：无；查看浏览器 Cookie 即可见。
- **影响范围**：本地隐私泄露，可被社工利用（暴露账号名）。
- **修复建议**：若保留此功能，至少标注为便利特性并在隐私说明中告知；或改为存储不可逆标识。

### DEF-014 管理员权限判定依赖会话中的 `role`，不实时回查数据库
- **位置**：`auth.py:124`（`admin_required` 仅 `session.get('role') != 'admin'`）、`auth.py:169`（can_edit_task 用 `user['role']`，而 user 来自 `get_current_user` 实时查库，此处正常）
- **类别**：逻辑
- **严重程度**：轻微
- **描述**：`admin_required` 信任会话里缓存的 `role`，若管理员在别处被降级/停用，其已登录的旧会话仍具管理员权限，直到重新登录才失效（`login_required` 会回查用户是否存在，但不回查角色）。属一致性问题，非越权漏洞（会话本身已签名防伪造）。
- **复现步骤**：
  1. 管理员 A 登录；
  2. 管理员 B 将 A 降级为 owner 或停用；
  3. A 的旧会话仍可通过 `admin_required` 访问管理接口，直至重新登录。
- **影响范围**：权限变更生效延迟，仅影响被改角色者自身会话。
- **修复建议**：`admin_required` 内改为 `get_current_user()` 实时取 `role`，或登录态失效时强制重登。

### DEF-016 登出后"您已安全退出"提示泄漏到再次登录后的首页
- **位置**：`templates/login.html`（登录页原缺少 flash 消息容器，也未引入 `main.js`）、`templates/base.html`（flash-container 由 `main.js` 渲染并自动消失）

  2. 同一会话下重新输入账号密码登录 → 进入 `/dashboard`；
  3. 首页顶部仍弹出"您已安全退出"提示。
- **影响范围**：所有登出后再次登录的用户；纯提示错乱，无数据风险。
- **修复建议**：在 `login.html` 增加与 base 一致的 flash-container，并引入 `main.js` 负责 toast 显示与自动消失，使 flash 在登录页即被消费。
- **修复状态**：已修复（commit `f7f63a6`，静态资源版本号 bump 至 `20260830ac`）。

### DEF-017 顶栏左上角品牌区（图标+系统名+日期）呈现可点击跳转态
- **位置**：`templates/base.html`（`.topbar-brand` 原为 `<a href="{{ url_for('dashboard.overview') }}">`）、`static/css/main.css`（`.topbar .topbar-brand` 未设 `cursor: default`）

## 五、重点风险提示

1. **最高优先级**：`DEF-001`（硬编码 SECRET_KEY）是本次审查中最严重的问题。它使"会话即身份"的整套鉴权形同虚设——任何拿到程序的人都能伪造管理员会话。建议作为修复第一顺位，且修复后需强制所有用户重新登录（旧会话签名失效）。
2. **连锁放大**：`DEF-001 + DEF-004（0.0.0.0 暴露）+ DEF-002（无 CSRF）+ DEF-005（弱口令/无锁定）` 叠加后，内网任意可达者即可接管系统。即便暂不整改全部，也应优先把 `HOST` 收回到 `127.0.0.1`（单机自查默认）并清理演示弱口令。
3. **稳定性**：`DEF-003`（并发写未加锁）在后台扫描与用户操作重叠时会产生偶发 500，建议在迭代中统一写路径至 `db.transaction()` 并开启 WAL。
4. **用户验收类 UI 缺陷已修复**：DEF-015（截止日期显示异常）、DEF-016（登出提示泄漏到首页）、DEF-017（顶栏品牌区误可点击）系用户截图反馈，已分别在 commit `a0c1b32` / `f7f63a6` 中修复；055（导出改 Excel）、056（图标 SVG 化）为体验增强，不计入缺陷。
4. **已核查但未发现问题（供参考）**：
   - SQL 注入：查询构造（`get_tasks` 的 `filters` 全部参数化、`sort` 走白名单 `order_map`）未发现注入点；仅 `update_task` 有潜在隐患（DEF-007）。
   - XSS：Jinja2 默认自动转义生效，模板未对用户数据使用 `|safe`；前端 `main.js` 的 `innerHTML` 仅注入服务端已转义片段或固定常量，未发现存储/反射 XSS 注入点。
   - 越权（IDOR）：`task_delete`/`task_remind`/证据与阻塞删除/发消息/`user_*`/`settings.system` 均正确校验 `admin_required` 或 `can_edit_task`；`mark_read` 校验消息归属。未发现越权读写他人数据。

> 说明：以上结论均基于静态代码审查，部分运行时行为（如 DEF-003 的并发触发、DEF-011 的竞态）建议通过实际压测/并发脚本进一步确认。
