### 原始需求复述

用户是编程新手，要在组织内部搭建一套**督办（任务督办/跟踪）系统**，解决四大痛点：
1. 任务分散在各处，难以统一管理
2. 进度难把控，不知道任务推进到哪了
3. 问题滞后暴露，容易造成工作延误
4. 缺乏闭环跟踪，事情容易不了了之

系统包含两个角色（管理员 admin、任务负责人 owner），采用统一任务池，支持站内消息通知，完全离线可用，无需运维部署。

---

## 二、产品目标

督办系统是一套**面向小团队的轻量级任务跟踪工具**，解决任务分散、进度失控、问题滞后、缺乏闭环四大痛点。它服务于组织内的管理员和任务负责人，核心价值是：**把所有任务收进一个池子，用清晰的状态流转和三层预警机制，确保每件事都有人跟、有人盯、有结果**。系统采用本地部署、零配置启动，让没有技术背景的用户也能开箱即用。

| A-US-03 | 作为管理员，我希望**在线推送站内消息给负责人**（如催办、补充指令），以便及时沟通而不依赖外部工具。 |

## 四、任务状态机（5 态）

### 4.1 状态定义

| 状态 | 名称 | 含义 | 颜色建议 |
|------|------|------|----------|
| S1 | **待启动** | 任务已创建但尚未开始执行。负责人还没动工。 | 灰色 |
| S2 | **进行中** | 任务正在推进中，负责人已开始执行。 | 蓝色 |
| S3 | **已逾期** | 超过截止日期仍未闭环。**这是一个独立状态**（不是标签），表示任务已出现风险，需要重点关注。 | 红色 |
| S4 | **已闭环** | 任务已完成，形成工作闭环。终态之一。 | 绿色 |
| S5 | **已撤销** | 任务不再需要执行（取消/作废）。终态之一。 | 深灰色（删除线样式） |

### 4.2 状态流转规则

**核心原则**：
- "已逾期"由系统**自动触发**：当任务处于"待启动"或"进行中"，且当前时间超过截止日期，系统自动将其状态变为"已逾期"。
- "已逾期"后，负责人可以手动改回"进行中"（表示重新开始推进），或直接"已闭环"/"已撤销"。
- "已闭环"和"已撤销"为终态，但允许管理员**重新打开**（→ 进行中），用于纠错。

### 4.3 状态转换矩阵

> 行 = 当前状态，列 = 目标状态。✅ = 允许转换，❌ = 不允许，🔄 = 系统自动触发。

| 当前\目标 | 待启动 | 进行中 | 已逾期 | 已闭环 | 已撤销 |
|-----------|:------:|:------:|:------:|:------:|:------:|
| **待启动** | — | ✅ 开始执行 | 🔄 超期自动触发 | ✅ 直接闭环 | ✅ 撤销 |
| **进行中** | ❌ | — | 🔄 超期自动触发 | ✅ 完成闭环 | ✅ 撤销 |
| **已逾期** | ❌ | ✅ 恢复推进 | — | ✅ 闭环（逾期完成） | ✅ 撤销 |
| **已闭环** | ❌ | ✅ 管理员重新打开 | ❌ | — | ❌ |
| **已撤销** | ✅ 重新激活 | ❌ | ❌ | ❌ | — |

**流转说明**：
1. **待启动 → 进行中**：负责人点击"开始"，或管理员推送消息后负责人响应。
2. **进行中 → 已闭环**：负责人/管理员标记完成，需填写完成说明。
3. **超期自动 → 已逾期**：系统定时检查（建议每 5 分钟扫描一次），将超期未闭环的"待启动"和"进行中"任务自动置为"已逾期"，并触发第二层预警。
4. **已逾期 → 进行中**：负责人更新进度后可手动改回，表示"我知道逾期了，正在推进"。
5. **已闭环 → 进行中**：仅管理员可操作，用于闭环后发现需要返工的情况。
6. **已撤销 → 待启动**：仅管理员可操作，用于误撤销后恢复。

## 五、三层预警机制

| 层级 | 预警名称 | 触发条件 | 提醒对象 | 提醒方式 | 频率 |
|------|----------|----------|----------|----------|------|
| **第一层** | 即将到期预警 | 任务截止日期前 **3 天**（含当天），且任务状态为"待启动"或"进行中" | 任务负责人 | 站内消息通知（红点 + 通知列表） | 每天 1 次（建议每日 09:00 扫描） |
| **第二层** | 已逾期预警 | 任务超过截止日期仍未闭环，状态已自动变为"已逾期" | 任务负责人 **+ 管理员** | 站内消息通知（红点 + 通知列表，标记为"逾期"高亮） | 触发时 1 次 + 每日提醒 1 次（建议每日 09:00） |
| **第三层** | 长期待激活预警 | 任务创建后超过 **7 天**仍未启动（状态仍为"待启动"） | 任务负责人 **+ 管理员** | 站内消息通知（红点 + 通知列表，标记为"待激活"） | 每 7 天提醒 1 次 |

**预警规则补充说明**：
- 三层预警可叠加：一个任务可能同时触发多层预警（如创建后 7 天未启动 + 距截止 3 天），系统会合并为一条通知，避免消息轰炸。
- 预警天数（3 天 / 7 天）可在管理员设置页调整，默认值如上。
- 预警触发后，通知列表显示任务标题、预警类型、触发时间，点击可直接跳转任务详情。
- 任务进入"已闭环"或"已撤销"后，该任务的所有预警自动停止。

## 九、待确认问题

以下问题需要用户进一步确认或决策，每个问题附选项供参考：

### Q1：技术栈选择

用户是编程新手，需要选择一套易于理解和维护、且便于本地打包部署的技术栈。

- **选项 A**：Python + Flask + SQLite + Jinja2 模板渲染（后端为主，前端简单）
  - 优点：Python 语法简洁，新手友好；单文件数据库；打包简单（PyInstaller）
  - 缺点：界面交互不如前端框架流畅
- **选项 B**：Python + Flask（后端 API）+ Vue 3（前端）
  - 优点：前后端分离，界面更接近 Linear 风格
  - 缺点：需要构建前端，打包稍复杂
- **选项 C**：Node.js + Express + SQLite + 前端模板
  - 优点：前后端统一 JavaScript
  - 缺点：对编程新手不如 Python 直观

**建议**：选项 A（Python + Flask + SQLite），最简单直接，适合新手。

### Q2：默认管理员账号方案

首次部署时如何提供初始管理员账号？

- **选项 A**：预置默认账号 admin / admin123，首次登录强制改密码
- **选项 B**：首次启动时弹出初始化向导，引导用户创建管理员账号
- **选项 C**：配置文件中预设，用户手动修改配置

**建议**：选项 B，最安全且用户体验好。

### Q3：预警天数默认值

即将到期预警（3 天）和长期待激活预警（7 天）是否合适？

- **选项 A**：3 天 / 7 天（当前方案）
- **选项 B**：1 天 / 3 天（更紧凑，适合高频督办场景）
- **选项 C**：5 天 / 14 天（更宽松，适合周期较长的任务）
- **选项 D**：可配置，管理员自行设置（默认 3 天 / 7 天）

**建议**：选项 D，灵活性最高。

### Q4：负责人查看全部任务的权限

任务负责人（owner）能否看到其他人的任务（只读）？

- **选项 A**：完全看不到别人的任务（数据隔离最严格）
- **选项 B**：能看到所有人的任务列表，但只能编辑自己的（信息透明，参考 Linear）
- **选项 C**：只能看到自己参与的任务

**建议**：选项 B，保持信息透明有助于团队协作，但权限严格限制为只读。

### Q5：已闭环任务是否允许重新打开

任务闭环后，如果发现需要返工，是否允许重新打开？

- **选项 A**：仅管理员可重新打开（当前方案）
- **选项 B**：负责人和管理员都可重新打开
- **选项 C**：闭环即终态，不允许重新打开（需新建任务）

**建议**：选项 A，避免随意重开，同时保留纠错能力。

### Q6：任务删除策略

任务是否支持物理删除（从数据库彻底移除）？

- **选项 A**：不支持删除，只能"已撤销"（软删除，保留记录可追溯）
- **选项 B**：管理员可物理删除已撤销的任务
- **选项 C**：所有用户可删除自己创建的任务

**建议**：选项 A，保证任务记录完整可追溯，符合督办系统的审计需求。

### Q7：启动脚本操作系统兼容性

打包的启动脚本需要支持哪些操作系统？

- **选项 A**：仅 Windows（.bat 启动脚本）
- **选项 B**：Windows + macOS（.bat + .command）
- **选项 C**：Windows + macOS + Linux（.bat + .command + .sh）

**建议**：确认用户主要使用的操作系统，先做 A，后续按需扩展。

### Q8：通知消息保留期限

站内消息是否需要自动清理过期消息？

- **选项 A**：永久保留所有消息
- **选项 B**：已读消息保留 30 天后自动清理
- **选项 C**：管理员可手动批量清理

**建议**：选项 A，数据量小（5-20人），无需自动清理，保留完整记录。

## 十一、V2 迭代增补

> **增补日期**：2026-08-28（V2 迭代开发完成后文档同步）
> **增补依据**：`iteration-v2-design.md`（Q1–Q9 已确认）+ V2 交付代码（4 批次：UI 底座 / 数据库迁移+仪表盘 / 抽屉交互 / 功能补全）

### 11.1 迭代概述

V2 在**完整保留 V1 全部功能**（批量操作、CSV 导出、用户管理、三层预警、初始化向导、PyInstaller 离线打包等，对应差异分析清单 C1–C12）的前提下，完成两类升级：

2. **功能补全**：任务新字段、过程证据、阻塞记录、闭环矩阵、推送提醒。

### 11.2 新增功能清单

#### V2-01 任务字段扩展：进度% / 风险点 / 协同方

> **用户价值**：负责人用一句进度数字 + 风险说明即可汇报进展，管理员不必逐条追问"推进到哪了、卡在哪"。

**功能点**：
- `tasks` 表新增 3 字段：`progress_percent`（进度%，整数 0–100）、`risk_note`（风险点，文本）、`collaborators`（协同方，文本，逗号分隔多人）
- 新建任务表单、编辑任务表单、任务详情独立页、任务详情抽屉（含行内编辑）均支持这 3 个字段
- 校验规则：进度必须是 0–100 的整数；风险点/协同方文本上限 500 字
- 抽屉详情页签顶部展示进度条 + 百分比，行内修改进度%后进度条即时联动刷新
- 编辑表单向后兼容：旧表单未携带这 3 个字段时保留原值，不清零

#### V2-02 过程证据与阻塞记录（新表）

> **用户价值**：任务推进中的关键凭据（文字说明/链接/文件名）和卡点（阻塞）有了专门的家，过程可追溯、卡点不沉没。

**功能点**：
- 新表 `evidence`（过程证据）：类型三选一 text（文字）/ link（链接）/ file（文件名，不真正上传文件）
- 新表 `blockers`（阻塞记录）：状态两态 open（待解决）/ resolved（已解决）
- 添加入口：任务详情抽屉"过程证据""阻塞记录"两个页签内的添加表单，AJAX 提交
- 权限：owner 可为自己的任务添加；admin 可为所有任务添加；阻塞"标记解决"仅 admin 或记录创建者本人
- 内容上限 500 字；所有增删/解决操作自动写入 `progress_logs` 时间线留痕（纯备注型日志，状态字段为空）

#### V2-03 抽屉交互体系（3 个抽屉）

> **用户价值**：查看和更新任务不再整页跳转，信息在原位滑入呈现，操作路径从"点开→跳页→返回"缩短为"点行→抽屉→关闭"。

**功能点**：
- **任务详情抽屉**：任务列表行点击（含仪表盘焦点列表）→ 右侧滑入抽屉，含"详情 / 过程证据 / 阻塞记录"3 个页签；详情页签支持全字段行内编辑、状态流转、进度时间线
- **Owner 抽屉**：仪表盘闭环矩阵点击负责人名字 → 该负责人名下任务列表抽屉（最多 50 条，按截止日期升序）
- **消息抽屉**：顶栏铃铛点击 → 最近 50 条消息抽屉，支持类型筛选、单条已读、全部已读；点击消息 → 标记已读 + 打开关联任务详情抽屉
- 原 `/messages` 独立消息中心页**移除**，旧链接 301 跳转到 `/dashboard`
- 原任务详情独立页 `/tasks/<id>` **保留**，用于消息跳转降级、JS 失效降级、浏览器直链三种场景
- 交互细节：ESC / 点击遮罩 / 关闭按钮均可关闭；操作成功后抽屉内容自动刷新（重新拉取片段，权限由服务端重算）

#### V2-04 仪表盘 V2

> **用户价值**：管理员一眼看清"总量—状态—谁在拖后腿"，按时间范围切换统计口径，督办例会的数据信手拈来。

**功能点**：
- 6 张可点击统计卡：任务总数 / 待启动 / 进行中 / 已逾期 / 已闭环 / 闭环率（点击跳转任务列表对应筛选）
- **今日督办焦点**列表：非终态任务按"已逾期 > 进行中 > 待启动"排序、同状态内按到期日升序，最多 20 条；当前用户负责的任务带"我的"标记
- **任务闭环矩阵**：列依次为 **负责人 / 任务数 / 待启动 / 进行中 / 已逾期 / 已闭环 / 已撤销 / 闭环率**（共 8 列，状态列使用完整状态名，不用缩写），按任务数降序，每页 8 人分页；点负责人名字开 Owner 抽屉，点数字跳任务列表带筛选
- **时间范围筛选**：全部 / 本年 / 本季 / 本月 / 本周下拉，按任务创建时间过滤，仅作用于仪表盘（统计卡 + 焦点 + 矩阵）
- 闭环率口径（Q9 已确认）：`closed ÷ (总数 − 已撤销)`，分母为 0 时显示"—"
- 原"我的待办"区块并入焦点列表；原 4 卡统计页由本页替代

#### V2-05 行内编辑接口

> **用户价值**：改一个字段不再进入整页编辑表单，点击字段、输入、回车即保存，督办更新像改表格一样轻。

**功能点**：
- 接口：`POST /tasks/<id>/field`（JSON 请求/响应）
- 字段白名单 8 个：`title` / `description` / `priority` / `due_date` / `progress_percent` / `risk_note` / `collaborators` / `assignee`
- 权限：复用 `can_edit_task`（admin 全部可改；owner 仅自己的任务，他人任务字段只读展示）；`assignee`（改派）额外仅 admin 可操作，改派成功自动给新负责人发站内通知
- 交互：点击字段值原位变输入框（文本/数字/日期/下拉/多行自适应），失焦或回车保存，ESC 取消；保存结果 Toast 反馈
- 服务端逐字段校验（标题非空且 ≤100 字、优先级枚举、日期 YYYY-MM-DD、进度 0–100、负责人存在且启用）

#### V2-06 证据 / 阻塞管理权限（删除仅 admin）

> **用户价值**：留痕数据不会被误删——负责人可自助记录，但销毁凭据的权限收归管理员，保证督办过程记录的严肃性。

**功能点**：
- 删除接口：`POST /tasks/<id>/evidence/<eid>/delete`、`POST /tasks/<id>/blockers/<bid>/delete`，**仅 admin**
- 删除前二次确认（浏览器 confirm）；AJAX 调用返回 JSON，普通 POST 重定向回详情页（双通道兼容）
- 删除操作同样写入进度时间线留痕；证据/阻塞必须属于对应任务，跨任务 ID 返回 404

#### V2-07 推送提醒

> **用户价值**：管理员在矩阵里发现某人逾期堆积，点一下"推送提醒"即可定向催办，不必切换到发消息页手写内容。

**功能点**：
- 接口：`POST /tasks/remind`（admin 专用），参数 `task_id`（提醒某任务的负责人，消息带任务标题/状态/截止日）或 `owner_id`（泛化提醒某负责人名下任务）二选一
- 实现：复用站内信系统，给目标负责人发一条 `admin_directive` 类型消息（Q8 已确认，不做邮件通道）
- 入口：Owner 抽屉顶部"推送提醒"按钮（仅 admin 可见）；不能给自己推送

#### V2-08 视觉体系重做（UI 底座）

> **用户价值**：界面从"能用"升级到"好用好看"：现代配色、状态一眼可辨、深夜加班有深色模式。

**功能点**：
- 布局：左侧边栏 → 顶部固定导航栏（概览/任务/设置/用户管理*/系统设置*，* 仅 admin），移动端收进汉堡菜单
- 视觉规范对齐模板：品牌蓝 #2563eb、卡片圆角 12px + 轻阴影 + hover 上浮、药丸状态标签（浅底深字 + 色点）、Toast 右下角通知（flash 消息自动转发为 Toast，flash 保留兜底）
- 状态徽章体系：`st-<status>` 类（st-pending 灰 / st-in_progress 琥珀 / st-overdue 红 / st-closed 绿 / st-cancelled 浅灰）；优先级彩色药丸（urgent 红 / high 橙 / medium 蓝 / low 灰），保留四级优先级（Q7）
- **深色模式**：顶栏一键切换，`html.dark` 切换全套 CSS 变量，偏好存 localStorage（默认浅色）
- 图标：Lucide SVG 以 Jinja2 宏（`templates/macros/icons.html`，约 25 个图标）内联输出，零外部依赖；字体走系统字体栈，不内嵌字体文件
- 登录页重做：左品牌介绍区 + 右登录卡，字段级错误提示（用户名/密码分开报错）、"记住我"用户名 cookie（30 天）、密码可见切换
- 技术约束不变：仍是 Flask + Jinja2 + 原生 JS + 单 CSS 文件，无构建工具，PyInstaller 离线打包零风险

### 11.5 兼容性说明

1. **老数据库自动升级**：V1 数据库启动时自动迁移（建新表 IF NOT EXISTS + `PRAGMA table_info` 检查缺列后 `ALTER TABLE ADD COLUMN`），秒级完成、数据不丢、可重复执行（幂等）；迁移异常仅记日志，不中断启动。
2. **旧链接兼容**：`/messages` 301 跳转 `/dashboard`，不产生 404；`/messages/send`、`/messages/read-all`、`/messages/unread-count` 等路由全部保留，由抽屉继续调用。
3. **登录接口**：登录失败返回 **401**（用户名或密码错误，不暴露账号是否存在）；用户名/密码为空返回 400 并定位到具体字段。
4. **V1 功能全量保留**：批量操作、CSV 导出（含中文文件名编码）、用户管理、系统设置、三层预警引擎、初始化向导、局域网部署与 PyInstaller 打包均正常，相关测试用例保留（消息中心页用例改为断言 301 跳转）。
5. **编辑表单向后兼容**：旧表单/客户端提交不含 3 个新字段时，字段保留原值不清零。

### 11.6 非目标重申（V2 明确不做）

以下为 V2 迭代范围外事项（详见 `iteration-v2-design.md` §9），避免误解为已实现：

1. **真实文件上传**：file 类证据仅记录文件名/可选链接，不上传文件本体
2. **邮件通道**：推送提醒仅走站内信（Q8 已确认）
3. **P0/P1/P2 三级优先级改造**：保留现有 urgent/high/medium/low 四级（Q7 已确认）
4. **前后端分离 / SPA 改造**：仍是 Flask + Jinja2 服务端渲染 + 原生 JS
5. **部门、来源会议、会议日期、任务资产 ID、引用原话字段**：Q1 已确认不新增
