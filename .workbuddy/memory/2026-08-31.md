### ⚠️ 本次最有价值的坑：哨兵值 0 的双重语义
限流记录用 `locked_until` 存解锁时刻，约定 **`0` = 从未被锁定**（此时仅在累积失败计数）。
但 `0` 同时也是「时间戳已过期」的合法取值，**两个函数各踩一次**：
```python
# is_login_locked：本意"锁定期已过则清记录"
remain = rec['locked_until'] - now   # 从未锁定时 = 0-now，负数
if remain <= 0: del _login_failures[key]   # ← 把正在累积的计数删了
# record_login_failure：本意"上轮锁定已过期则重数"
if rec and rec['locked_until'] <= now:     # 0 <= now 恒真
    rec = None                              # ← 每次丢弃，重新从 1 数
```
**后果**：计数永远停在 1，限流完全不生效；但日志在打、提示在显示「还可尝试 2 次」、
测试也不报错 —— 只是那个「2」永远是 2。修复：`0 < rec['locked_until'] <= now`，两处补注释。

**教训（通用）**：
1. 用哨兵值表达「尚未发生」时，必须在**每一个**读取点显式排除，
   不能指望比较运算符顺带处理（`0 <= now` 语义上是「过期」，不是「未设置」）。
2. 这类 bug 只有**连续调用 3 次以上**观察计数是否累加才能发现，单次调用行为完全正确。
   本次是靠验证脚本逐次打印「剩余 N 次」，看到三次都是 2 才察觉。
3. 写状态机时，验证脚本要覆盖「完整周期」而不是只验证单点。
