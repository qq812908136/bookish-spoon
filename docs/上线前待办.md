## 二、详细项

### ✅ DEF-001 会话签名密钥硬编码 —— 已修复（2026-08-31）

- **位置**：`src/config.py`（`SECRET_KEY = _env_str('SECRET_KEY') or _load_or_create_secret_key()`）
- **严重程度**：严重
- **风险描述**：Flask 会话 Cookie 仅由 `SECRET_KEY` 签名（不加密）。原实现把密钥写死在源码中（`task-supervision-system-local-secret-key-2025`），会随 exe/源码分发给所有部署方，已无秘密性。任何能拿到程序的人都能伪造任意用户（含管理员）会话 Cookie，无需密码即可登录。
- **修复方式**：密钥不再有默认值，改为
  1. 环境变量 / `.env` 显式配置（运维需要共享会话或轮换时使用）；
  2. 否则首次启动用 `secrets.token_hex(32)` 生成并写入 `data/secret.key`，之后一直复用。
- **验收标准达成情况**：

  | 标准 | 状态 | 证据 |
  |---|---|---|
  | 源码与打包物中不再包含固定 `SECRET_KEY` | ✅ | `grep -rn "task-supervision-system-local-secret" src/` 无命中 |
  | 不同部署实例使用不同密钥 | ✅ | 两个独立实例分别生成 `0161406d...` 与 `e8f5602d...`，互不相同 |
  | 重启后复用同一密钥 | ✅ | 二次启动取回同一把 `a3c51f4b...`（会话不中断） |

- **配套防护**：
  - `data/secret.key` 已加入 `.gitignore`，并在构建脚本的 `IGNORE_NAMES` 中排除 —— **不会随交付包分发**（否则所有实例共用同一把密钥，修复等于白做）。
  - 部署目录只读、无法落盘时，退回内存随机值继续运行（代价是重启后会话失效），**不阻断启动**。
- **遗留提示**：现有部署升级后密钥会变化，所有用户会被强制重新登录一次，属预期行为。

### ✅ DEF-002 全站缺少 CSRF 防护 —— 已修复（2026-09-01）

- **位置**：新增 `src/csrf.py`；接入点 `src/app.py`（`before_request` + 模板上下文）、`src/config.py`、`src/auth.py`（登录轮换）、21 个模板表单、`src/static/js/main.js`
- **严重程度**：一般
- **风险描述**：此前所有写操作路由均无 CSRF 令牌校验。已登录用户访问恶意页面时，攻击者可借其身份发起伪造请求（删任务、改状态、建管理员账号等）。

#### 已完成的整改

1. **核心模块 `src/csrf.py`**：令牌 = `过期时间戳 + HMAC-SHA256(会话密钥, 时间戳)`，校验时现算并做常量时间比较。
2. **全局钩子**：`app.py` 的 `before_request` 统一校验所有非安全方法（POST/PUT/PATCH/DELETE）。**放在钩子里而不是逐路由加装饰器**，是为了让将来新增的 POST 路由默认就受保护。
3. **模板注入**：上下文处理器注入 `csrf_token`，21 个 `method="POST"` 表单全部带上 hidden 字段（跨 10 个模板）。
4. **AJAX 注入**：`base.html` 输出 `<meta name="csrf-token">`，`main.js` 用统一的 `csrfHeaders()` 为 8 处写请求注入 `X-CSRF-Token` 头。
5. **登录轮换**：登录成功时调用 `rotate_csrf_token()`，登录前签发的令牌作废。
6. **配置开关**：`CSRF_ENABLED`（默认 true）、`CSRF_TOKEN_MAX_AGE`（默认 86400 秒）。

#### 令牌携带方式（三选一，服务端都认）

| 方式 | 适用场景 | 示例 |
|---|---|---|
| 表单字段 `csrf_token` | 普通表单提交 | `<input type="hidden" name="csrf_token" value="{{ csrf_token }}">` |
| 请求头 `X-CSRF-Token` | fetch / XHR | `headers: csrfHeaders()` |
| JSON body 的 `csrf_token` 键 | JSON 接口 | `{"field": "x", "csrf_token": "..."}` |

#### 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 依赖 | **自研，不引入 Flask-WTF** | 新增依赖要同时改 requirements.txt、PyInstaller spec 的 hiddenimports、托管解释器、重新打包 exe 四处；核心逻辑不到 150 行，自己写更可控 |
| 令牌形态 | **带过期时间的签名令牌**（非固定字符串比对） | 固定令牌一次只能有一个有效值，多标签页会互相作废；签名令牌是现算的，同会话下多个令牌在有效期内可并存 |
| 校验位置 | **`before_request` 全局钩子** | 逐路由加装饰器依赖人不遗忘；新路由默认受保护 |
| 失败响应 | AJAX 返回 JSON，页面返回 400 提示页 | 前端按 `success`/`message` 解析，返回整页 HTML 会让 `r.json()` 直接抛异常 |
| 状态码 | **400 而非 403** | 403 已被 `admin_required` 用于「权限不足」；两者混用会让用户和日志都分不清是权限问题还是安全拦截 |
| 登录时轮换 | 轮换会话密钥 | 登录前后的身份是两回事，不让登录前的令牌继续用于登录后的写操作 |

#### 验收标准达成情况

| 标准 | 状态 | 证据 |
|---|---|---|
| 所有状态变更请求需携带有效 CSRF 令牌 | ✅ | 全量遍历 url_map，24 条写路由无一例外（`test_all_write_routes_require_token`） |
| 缺失/无效令牌的请求被拒绝 | ✅ | 返回 400 + 「请求未通过安全校验」；AJAX 返回 JSON，页面返回 400 提示页 |
| 现有功能不受影响 | ✅ | 全量测试套件通过（含 103 处 `.post()` 的业务用例） |
| 表单全部带上令牌 | ✅ | 扫描 10 个模板共 21 个 POST 表单，0 遗漏（`test_every_post_form_has_token_field`） |
| AJAX 全部带上令牌 | ✅ | 扫描 `main.js`，8 处写请求 0 遗漏（`test_mainjs_injects_token_into_every_write_fetch`） |
| 跨会话令牌不可复用 | ✅ | 另一会话的令牌被拒（`test_token_not_transferable_to_another_session`） |
| 过期令牌失效 | ✅ | 超过 `CSRF_TOKEN_MAX_AGE` 的令牌被拒 |

- **新增测试用例**：`TestCSRF` 共 16 项，其中 3 项为**防回归**用例（遍历路由 / 扫描模板 / 扫描 JS），将来新增写路由或表单漏带令牌会直接失败。

- **遗留提示**：
  - `SameSite=Lax`（DEF-004 配套）依然保留，作为**第二道防线**。两者互不依赖，任一层被绕过时另一层仍起作用。
  - 页面停留超过 `CSRF_TOKEN_MAX_AGE`（默认 24 小时）后提交会提示刷新。抽屉类 AJAX 操作会在每次加载时用新签发的令牌刷新 meta 标签，长时间开着页面不易触发；普通表单页面若确实需要，可把该值调大。
  - `csrf_exempt` 装饰器仅用于确实无副作用的内部接口，**写操作路由一律不要加**。

### ✅ DEF-005 登录无频率限制、无弱口令校验 —— 已修复（2026-08-31）

- **位置**：`src/auth.py`（限流状态机 + `check_password_strength`）、`src/config.py`（4 个新配置项）、4 个设置密码的路由
- **严重程度**：一般
- **风险描述**：登录接口无失败计数，攻击者可对 `admin` 无限次尝试密码（演示数据中曾使用 `admin/admin123`、`owner/123456` 弱口令）；同时系统对新建/修改密码**完全没有强度要求**，初始化向导只校验 `len >= 6`，`123456` 这类密码可正常使用。

  > 📌 2026-09-01 更新：演示库弱口令已清理——`admin` 与 8 位负责人口令改为强口令（`Supv#Admin2026` / `Supv#Owner2026`），种子脚本与初始化向导同步更新；此项风险已闭环。

#### 已完成的整改

**1. 登录失败限流**

| 项 | 说明 |
|---|---|
| 计数维度 | **客户端 IP + 用户名** 组合键 |
| 阈值 | 连续失败 `LOGIN_MAX_ATTEMPTS`（默认 5）次后锁定 |
| 锁定时长 | `LOGIN_LOCKOUT_MINUTES`（默认 15）分钟，从**最后一次失败**起算 |
| 锁定期间 | **即使密码正确也拒绝**（否则限流形同虚设） |
| 解锁方式 | 到期自动解锁；登录成功立即清零计数 |
| 失败提示 | 递减提示「还可尝试 N 次」；锁定后提示剩余等待时间 |

为什么是「IP + 用户名」而不是单一维度：
- 只看 IP —— 整个办公室共用一个出口 IP 时会互相误伤；
- 只看用户名 —— 攻击者拿常用密码遍历用户名时毫无阻挡。

**2. 弱口令拦截**（`check_password_strength`）

| 规则 | 示例（被拦截） |
|---|---|
| 长度 ≥ `PASSWORD_MIN_LENGTH`（默认 8） | `Ab1` |
| 不能全是数字 | `12345678` |
| 不能全是字母 | `abcdefghij` |
| 不在常见弱口令黑名单内（比较不区分大小写） | `password123`、`Admin1234`、`QWERTY123` |
| 不能与用户名相同 | 用户名 `zhangsan88`、密码 `zhangsan88` |

刻意**不做**「必须大小写 + 特殊符号」这类强组合要求 —— 内部督办系统用不上，门槛太高只会让人把密码贴到显示器上。

**3. 覆盖全部 4 个设置密码的入口**
初始化向导、新建用户、重置密码、个人改密码 —— 此前只有初始化向导有一句 `len >= 6`。

#### 关键设计决策

- **不追溯已有账号**：历史遗留的 6 位弱密码账号**仍可正常登录**，只在下次改密码时才要求达标。避免一次升级把所有老用户锁在门外。
- **计数存内存而非数据库**：限流状态是短时效的，重启后清零不影响防护效果（攻击者无法触发重启给自己解锁）；同时避免「一次请求换一次磁盘 I/O」给爆破者提供放大杠杆，也免去数据库迁移。
- **多进程部署的已知限制**：计数是进程内的，若用 gunicorn 多 worker 部署，各 worker 会独立计数（实际效果 = 阈值 × worker 数）。本项目是单进程形态（Flask 开发服务器 / waitress），不触发。
- **反向代理下的注意事项**：部署在 Nginx/Caddy 后面时，需在代理层正确传递客户端 IP，否则所有请求都记成代理服务器的 IP，会导致**一人被锁、全员陪绑**。详见 `docs/生产部署指南.md`。

- **验收标准达成情况**：

  | 标准 | 状态 | 证据 |
  |---|---|---|
  | 连续失败达阈值后锁定 | ✅ | 19 项专项用例全通过（含计数递减、锁定、到期解锁） |
  | 锁定期内正确密码也被拒 | ✅ | 锁定后以正确密码请求，仍返回 401 且未建立会话 |
  | 到期自动解锁 | ✅ | 等待锁定期过后恢复登录，无需人工干预 |
  | 登录成功清零计数 | ✅ | 成功后重新从满额计数，不累积旧账 |
  | IP / 用户名两个维度隔离 | ✅ | 同 IP 不同账号、同账号不同 IP 互不影响 |
  | 4 个入口均拦截弱口令 | ✅ | 弱口令提交后密码哈希未被改写、账号未落库 |
  | 已有弱口令账号仍可登录 | ✅ | 6 位密码老账号正常登录（不追溯） |
