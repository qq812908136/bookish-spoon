## 四、构建 / 交付链路

```
源码根 ──(督办系统.spec 或 build.bat)──▶ dist/督办系统/{督办系统.exe, _internal}
                                              │ 手工同步
                                              ▼
                              deliverables/v3/05_离线程序/督办系统/{exe, _internal, data, *.bat}
源码根 ──(build_delivery_package.py: v2 → v3)──▶ deliverables/督办系统-交付包-v3/
                                              │ 压缩
                                              ▼
                                    deliverables/督办系统-交付包-v3.zip（229 条目）
test_suite.py ──(generate_test_report.py)──▶ 04_测试/*（md + html + json）
```

三条链路彼此独立、无自动化串联，是本次梳理发现的**主要维护风险点**（改一次源码要手工跟到 4 个地方：源码库、交付包 03_开发代码、05_离线程序/_internal、zip）。

## 六、整理建议（按优先级）

## 七、一句话结论

项目**运行时结构清晰**（config → db → models → routes → templates/static 的分层与依赖方向干净，无循环依赖），混乱集中在**非运行时部分**：根目录承载了源码之外的脚本、测试、构建产物和历史 zip；交付物存在三版本 + 双 zip 的重叠；文档在 `docs/` 与 `deliverables/01-04` 之间双向复制、命名不一致。按 P0→P1 两步清理即可回收约 **62MB** 冗余（build 21M + 发行版 zip 13.6M + v1/v2 目录 57M 中已归档部分），并让"源码根"回到只放应用代码的状态。
