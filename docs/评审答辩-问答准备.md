# 督办系统评审答辩 · 问答准备稿

> 用途：AI 应用实践任务（任务二·督办系统）评审答辩。
> 评审考察的核心是 **「你用 AI 工具解决问题的能力」**，不是「假装系统是人写的」。
> 所以答辩的总基调：**大方承认 AI 是编码主力，重点展示你如何驾驭它**。

---

## 〇、答辩总策略（先记住这三条）

1. **诚实是最大的加分项。** 评审目的写得很清楚——「挖掘 AI 应用能力突出的人员」。藏着掖着反而跑题。你要展示的是：需求定义、方案决策、质量把关、问题诊断都是你在掌舵，AI 是你的开发团队。
2. **结论先行 + 真实案例 + 数据支撑。** 每个问题先给一句话结论，再讲一个真实发生过的例子，最后落到数字（数字见文末速记卡）。
3. **不会的不硬编。** 说「这个点我记下来，会后验证后回复」比瞎答强十倍。

## 一、预设问题参考回答（口语稿，可直接照着说）

### Q1：任务拆解——怎么做的？什么思路？用什么工具？大概的计划？

**一句话结论：** 先收敛需求再写代码，按「版本迭代」纵向拆、按「交付单元」横向拆。

**展开（照说）：**

我做的第一件事不是写代码，而是把需求锁死。我给自己定了一条铁律：**SPEC 不定稿，一行代码都不动**。先把核心决策收敛掉——2 种角色、统一任务池、5 态状态机、3 层预警、站内信加邮件双渠道——这些定下来之前，全是讨论，不写码。

然后纵向按版本拆：

- **V1 核心闭环**：任务的增删改查 + 5 态状态机 + 站内信，先让「建—跟—闭环」这条主线跑通；
- **V2 安全加固**：CSRF 防护、登录限流、弱口令拦截、密钥管理；
- **V3 稳定化**：打磨细节、修缺陷；
- **V4 邮件子系统**：55 项需求 SPEC，加密存储、去重、熔断；
- **V5 AI 增强**：AI 催办话术、结构化建任务、督办简报。

每个版本横向再拆成固定的交付单元：**源码 → 测试 → 打包 exe → 交付包 → 文档闭环 → git 提交**，走完一个闭环才算完。

**工具上**：AI 编程助手做结对开发，Git 管版本，文档库沉淀所有决策，技术上选 Python + Flask + SQLite，PyInstaller 打成单个 exe，内网 Windows 双击即用。

**计划上**：一周周期里核心功能先行，安全和体验穿插，AI 增强放最后——这样任何时候停下来，手上的都是一个能交付的完整版本。

### Q2：使用工具的心得？步骤？

**一句话结论：** 把 AI 当「新员工」带，而不是当「搜索引擎」用。

**展开（照说）：**

我的心得有五条，都是踩坑踩出来的：

1. **给背景、给约束、给验收标准**，而不是一句「帮我写个 XX」。就像带新人，你不告诉他项目的目录规范、术语约定，他写出来的东西一定对不上。
2. **苏格拉底式交互**：我不直接下命令，让 AI 给我编号选项，我逐条确认。方向跑偏的成本远高于多问一轮。
3. **SPEC 锁定前不动代码**：需求漂移是 AI 协作最大的坑，比代码 bug 贵得多。
4. **小步增量、每步验证**：单次改动不超过一个交付单元，改完立刻跑测试。我们全量测试 181 项，每次提交前都过一遍。
5. **文档是第二记忆**：AI 会话会断，所有决策、约定、踩过的坑都落到文档里，新会话进来 5 分钟就能接上上下文。

**典型工作步骤**：我描述需求 → AI 产出 SPEC → 我评审确认 → AI 实现 → 测试验证 → 文档闭环 → 提交。每一步都有我的人工审批门，AI 的任何产出不过我这关，进不了主干。

### Q3：遇到什么问题？怎么解决的？

**一句话结论：** 问题主要三类——AI 代码的隐蔽 bug、环境的静默失败、平台编码坑，每个都沉淀成了规矩。

**展开（挑案例讲，2–3 个就够）：**

**案例一：AI 写的代码看着对、其实是错的。** 开发 AI 简报功能时，AI 生成的代码有四个隐蔽 bug：比如邮件类型常量只在标签字典里引用了、却没定义，运行即 NameError；还有一个更隐蔽——站内信收件人逻辑被邮件订阅条件误伤，导致没配邮箱的管理员连站内信都收不到。**解法：测试驱动。** 我要求每个功能配专项测试用例，这次 7 个用例当场把四个 bug 全摁在提交之前，然后 181 项全量回归兜底。AI 代码不过测试，不许提交。

**案例二：静默失败，报错都没有。** 推送代码时 github.com 被代理拦死（502），但 api.github.com 是通的——我没有瞎试，先诊断确认是网络策略问题，然后改走 GitHub 数据 API 完成推送。类似的还有 Git 分支名带斜杠时创建「假成功」——reflog 写了、分支文件没落盘。我对比两个目录才发现是被静默回滚了。**解法：不猜，先诊断；诊断清楚再绕路。**

**案例三：Windows 平台细节。** bat 脚本必须 GBK + CRLF 编码，UTF-8 直接乱码；打包时 dist 目录被资源管理器钉住句柄报权限错误。**解法：把坑固化成工具**——写编码校验脚本、删除前先改名移走、定位占用进程再解除。

每个坑解决完我都落进文档，下次同类问题 5 分钟闭环。

### Q4：AI 做不出自己想要的效果时，如何处理？

**一句话结论：** 先判断是「需求没说清」还是「能力到边界」——九成是前者；真不行就降级人工兜底，但绝不交付半成品。

**展开（照说）：**

第一步，**先怪自己**。AI 做不出想要的效果，九成是我的需求没给清楚。处理方式是把任务再拆小、把上下文补齐、给一个期望输出的样例，让它照着对齐。

第二步，**换交互方式**。从「命令式」换成「选项式」——让 AI 给我两三个方案，我选一个再让它细化。比来回返工快得多。

第三步，**降级人工兜底**。核心思路我自己给，让 AI 补细节；它做整体架构不行，就做局部实现。

第四步，也是最体现原则的一条——**效果不达标，宁可不做，也不交付半成品**。这次的 AI 督办简报功能就是这样：代码已经实现、测试也全过了，但我评估生成质量还没到能拿出去演示的水准，所以演示里我主动把它撤下，只展示稳定的督办闭环。**驾驭 AI 不只是让它干活，也包括知道什么时候该喊停。**

## 二、预判：评审还可能问的问题（按危险度排序）

### A 类：成果真实性（最尖锐，必问）

**Q5：这个项目 AI 参与度多少？你自己写了多少代码？**
> 如实说：AI 是编码主力，我负责需求定义、架构决策、逐版评审、质量验收和问题诊断——相当于「产品经理 + 架构师 + QA」角色，AI 是我的开发团队。然后立刻补一句证明掌控力的话：**「系统里任何一个模块的实现原理我都可以现场讲，比如预警引擎的去重逻辑、CSRF 的双层校验……」**（提前准备 2–3 个能脱稿讲的模块。）

**Q6：以后 AI 不在了，你能维护吗？**
> 能。底气是两样东西：一是文档唯一真相源，所有设计和决策都落了文档；二是 181 项自动化测试，任何改动跑一遍就知道有没有改坏。AI 是加速器，不是拐棍。

**Q7：你说踩了那么多坑，挑一个 AI 完全搞不定、必须靠人的？**
> 环境类问题：比如 Git 静默失败、句柄占用、代理拦截——这些 AI 给不出答案，因为它看不到我的机器。靠的是系统性诊断：先复现、再定位、再验证。

### B 类：技术与安全

**Q8：为什么用 Flask + SQLite + 单体 exe，不用大框架？**
> 场景决定的：内网离线部署、使用者是非技术同事，要求一台 Windows 双击即用、零依赖。SQLite 免安装数据库，单体 exe 免装运行时。如果将来上量，有 Waitress + HTTPS 的生产部署预案。

**Q9：数据安全怎么保证？**
> SMTP 密码加密入库、不进日志不明文展示；会话密钥落盘限权限；CSRF 双层防护；登录失败限流锁定；弱口令拦截。这些在 V2 做过一轮专项安全整改。

**Q10：并发、性能扛得住吗？**
> 定位是组织内部数十人规模，绰绰有余；预警走 5 分钟异步扫描 + 按人去重限流，不会阻塞页面。更大规模有升级路径。

### C 类：业务价值

**Q11：解决什么真实痛点？**
> 就是任务书里的原话：任务分散、进度难把控、问题滞后暴露。统一收口 + 自动盯办 + 闭环留痕，逾期不再靠人记。

**Q12：和任务一（风险管控平台）比，你的差异点？**
> 我选了自己最熟悉的督办场景，能把细节做透：可重开的闭环、三层预警、按人去重、双渠道触达。小而完整，比大而全更能落地。

**Q13：效果如何衡量？**
> 三个指标：逾期任务可见率（从靠人问到系统全量标红）、闭环率（看板直接出）、催办人力节省（预警自动触达替代人工催）。

### D 类：过程与成本

**Q14：一周时间怎么安排的？**
> 前两天需求收敛 + V1 主线，中间安全加固和邮件子系统，最后 AI 增强 + 全量测试 + 文档收尾。每个晚上跑全量回归，保证每天手上都是可交付状态。

**Q15：如果重做一遍，哪里会做得不一样？**
> 两点：测试应该更早引入（第一版是事后补的）；文档规范应该第一天就定（中途返工过一次目录结构）。

### E 类：推广与规划（呼应评审目的）

**Q16：这套 AI 协作方法能复制给其他同事吗？**
> 能，而且已经沉淀成 SOP 了：SPEC 先行 → 增量交付 → 测试兜底 → 文档闭环 → 人工审批门。这套流程不依赖特定项目，换个业务场景照用。

**Q17：系统后续怎么规划？**
> 三步：先小范围试点导入真实任务跑两周；根据反馈微调预警阈值和通知方式；AI 简报等生成质量打磨到我满意再正式启用。之后评估企微/钉钉集成。

### F 类：系统功能追问（演示后）

**Q18：逾期怎么判定？会不会误报？预警会不会轰炸？**
> 纯机器判定：截止日 + 实际状态，不靠人填，不漏也不凭空造。预警有按人按天去重，同一任务同一人同一天同类只发一条。

**Q19：手机上能用吗？多人多部门怎么管？**
> Web + H5 响应式，手机浏览器直接用。权限按角色隔离：管理员看全局，负责人只看自己名下。

## 四、雷区提醒

1. **别说「代码都是我自己写的」**——评审主题就是 AI 应用，这句话既不诚实也跑题。
2. **别神化 AI，也别贬低 AI**——定位是「我驾驭的工具/团队」。
3. **演示不碰 AI 功能**（已决定），被追问就说：「基础版已实现且测试通过，但生成质量我还想再打磨，所以演示聚焦稳定的核心闭环」——把「藏」说成「质量门槛」，反而加分。
4. **别硬答不会的**——记下来、会后回复，是专业表现。
5. **提前演练一遍 demo 流程**，评审现场网络/环境出状况时，先讲架构和设计文档兜底，别卡在现场调试。
