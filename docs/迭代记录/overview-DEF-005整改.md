# 执行概览：DEF-005 登录限流与弱口令拦截

> 完成时间：2026-08-31（提交前）
> 严重程度：**P1（一般）** —— 上线前安全整改清单的第三项
> 影响范围：登录接口、密码设置的 4 个入口、部署配置

---

## 一、问题是什么

两件事叠在一起，让内网里的任何人都有可能试出管理员密码。

**其一，登录没有失败次数限制。** 改之前 `do_login` 只做「查用户 → 验密码 → 写 session」三步，
对失败次数没有任何记录。写个脚本对 `/login` 循环提交口令字典，可以一直试到命中为止。

**其二，系统对密码强度几乎没有要求。** 全代码库只有初始化向导里有一句 `len(password) < 6`。
更麻烦的是演示数据本身就用的弱口令：`admin/admin123`、`owner/123456`。
这几个账号如果没清理就交付，爆破的难度接近于零。

---

## 二、修复方案

### 2.1 登录失败限流

计数维度是**客户端 IP + 用户名**的组合键。两个维度缺一不可：

| 维度 | 只用它的后果 |
|---|---|
| 只看 IP | 整个办公室共用一个出口 IP 时会互相误伤 |
| 只看用户名 | 攻击者拿常用密码遍历用户名时毫无阻挡 |

行为：连续失败 5 次（`LOGIN_MAX_ATTEMPTS`）后锁定 15 分钟（`LOGIN_LOCKOUT_MINUTES`），
从**最后一次失败**起算。锁定期内**即使输入正确密码也拒绝** —— 这一点是关键，
否则攻击者只要穿插一次正确密码就能把计数清零，限流形同虚设。

失败时提示「还可尝试 N 次」，让用户知道还剩几次机会；被锁后提示剩余等待时间。

### 2.2 弱口令拦截

新增 `check_password_strength(password, username)`，规则：

| 规则 | 说明 |
|---|---|
| 长度 ≥ 8（可配） | `PASSWORD_MIN_LENGTH` |
| 不能全是数字 | 挡 `12345678` 这类长度够但强度为零的 |
| 不能全是字母 | 挡 `password` |
| 不在常见弱口令黑名单内 | 约 50 个高频口令，比较时不区分大小写 |
| 不能与用户名相同 | 挡 `admin/admin` |

刻意**不做**「必须大小写 + 特殊符号」这类强组合要求。内部督办系统用不上这么严的门槛，
要求太高只会促使人把密码写到便利贴上贴显示器。

### 2.3 覆盖全部 4 个设置入口

此前只有初始化向导有一句长度校验，现在统一接入：

| 入口 | 文件 |
|---|---|
| 初始化向导 | `src/routes/auth_routes.py`（`setup`） |
| 新建用户 | `src/routes/user_routes.py`（`user_new`） |
| 重置密码 | `src/routes/user_routes.py`（`user_reset_password`） |
| 个人改密码 | `src/routes/settings_routes.py`（`profile`） |

重置密码那条顺带调整了顺序：原来先校验长度再查用户，现在**先查用户** ——
因为「密码不能与用户名相同」这条规则需要拿到目标用户的用户名。

前端三个模板（`setup.html` / `settings/profile.html` / `users/manage.html`）的
placeholder 也从写死的「至少6位」改为读 `{{ password_min_length }}`，
并补上 `minlength` 属性。配置项改了，提示文案会自动跟着变。

### 2.4 反向代理支持（顺带补齐）

限流依赖客户端 IP。部署在 Nginx / Caddy 后面时，应用看到的来源 IP 全是代理服务器的地址，
结果就是**一人被锁、全员陪绑**。

新增 `BEHIND_PROXY` 开关（**默认关闭**）+ `BEHIND_PROXY_TRUSTED_HOPS`，
开启后用 Werkzeug 的 `ProxyFix` 按 `X-Forwarded-For` 取真实 IP。

默认关闭是刻意的：开启意味着**信任** `X-Forwarded-*` 请求头，
如果实际并没有代理在前面，攻击者可以自己伪造这个头绕过限流。
`TRUSTED_HOPS` 也必须等于实际代理层数，填大了会留出伪造空间。

## 三、踩到的坑：哨兵值 0 的双重语义

这是本次改动最有价值的一条经验 —— **同一个语义陷阱在两个函数里各踩了一次，
而且都表现为「功能看起来生效了，但实际从不触发」**。

限流记录用 `locked_until` 字段存解锁时刻，并约定 **`0` 表示「从未被锁定过」**
（此时只是在累积失败计数）。问题在于，`0` 同时也是「时间戳已过期」的合法取值：

```python
# is_login_locked()：本意是"锁定期已过则清除记录"
remain = rec['locked_until'] - now      # 从未锁定时 = 0 - now，是个负数
if remain <= 0:
    del _login_failures[key]            # ← 把正在累积的计数删掉了
    return 0

# record_login_failure()：本意是"上一轮锁定已过期则重新计数"
if rec and rec['locked_until'] <= now:  # 0 <= now 恒为真
    rec = None                          # ← 每次都丢弃记录，重新从 1 数
```

**后果**：每一轮都从 1 重新开始数，计数永远达不到阈值，限流完全不生效。
而且表面上一切正常 —— 日志在打、提示在显示「还可尝试 2 次」、测试也不报错，
只是那个「2 次」永远是 2。

**教训**：
1. 用「哨兵值」表达「尚未发生」时，必须在**每一个**读取它的地方显式排除，
   不能指望比较运算符顺带处理（`0 <= now` 在语义上是「过期」，不是「未设置」）。
2. 这类 bug 只有**走完整状态机**才能发现 —— 单次调用的行为完全正确，
   必须连续调用 3 次以上看计数是否累加。本次是靠验证脚本里逐次打印
   「剩余尝试 N 次」发现的：三次打印都是 2，一眼看出不对。
3. 修复方式是把判断收紧为 `0 < rec['locked_until'] <= now`，
   并在两处都补了注释说明「0 表示从未锁定，不能当成过期」。

## 四、关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 计数存哪 | **内存**（非数据库） | 短时效状态，重启清零不影响防护（攻击者无法触发重启解锁）；避免「一次请求换一次磁盘 I/O」给爆破者提供放大杠杆；免去数据库迁移 |
| 是否追溯老账号 | **不追溯** | 历史遗留的 6 位密码账号仍可登录，只在改密码时要求达标 —— 否则一次升级把所有老用户锁在门外 |
| 提示剩余次数 | **提示** | 真实用户手滑输错时很有用；且不泄露账号是否存在（账号不存在时同样计数递减） |
| 多进程部署 | 各进程独立计数 | 已知限制，已写入文档。本项目是单进程形态（Flask 开发服务器 / waitress），不触发 |
| 是否强制强组合 | **否** | 内部系统门槛过高会促使写密码到纸上 |

另外给 `_client_ip()` 加了请求上下文兜底：脱离请求上下文调用时返回占位值而不是抛
`RuntimeError`，这样命令行脚本、单元测试直接调用限流函数都不会崩。
